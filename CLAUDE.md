# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"나만의 SOOP 확프" — a Manifest V3 Chrome extension for Soop (sooplive.com, formerly AfreecaTV). No bundler, no framework, no package.json: every file in `src/` is a plain script loaded directly by `manifest.json`. There is no build step.

## Commands

There is no build/lint/test tooling in this repo. Development loop:

- **Syntax-check a file after editing it**: `node --check src/<file>.js` (works for both classic scripts and the ES-module `background.js`/`soopLiveApi.js` on modern Node).
- **Validate manifest.json**: `node -e "JSON.parse(require('fs').readFileSync('manifest.json','utf8'))"`.
- **Manual test**: load unpacked at `chrome://extensions` (enable Developer mode → "압축해제된 확장 프로그램을 로드합니다" → select the repo root), then reload the extension after each change.
- **Background logs**: `chrome://extensions` → this extension's "service worker" link opens its DevTools console.
- **Content script logs** (panel, live monitor, etc.): open DevTools on the relevant `play.sooplive.com` tab.

## Architecture

### No bundler ⇒ shared JS world per content_scripts entry

Content scripts listed together in one `content_scripts` entry of `manifest.json` execute in the same isolated-world JS context on that page, so top-level `const`/`function` names in one file are visible to the others in the same entry and can collide. `content.js` and `songSearch.js` rely on this (deliberately share globals like `SongSearch`). Scripts that don't need to share state (`disableAutoPlay.js`, `hideBroadcastButton.js`, `liveMonitor.js`) are wrapped in an IIFE — keep doing this for new standalone content scripts.

`background.js` is the only ES module (`"type": "module"` in manifest) and is the only place that can `import` from `soopLiveApi.js`.

### Settings: one storage key, feature-gated

All configuration lives under a single `chrome.storage.local` key, `settings`, shaped as `{ features: { <featureName>: {...} } }`. Each feature object has at minimum `enabled: boolean`. This schema is intentionally duplicated (not shared via an imported module) as `DEFAULT_SETTINGS` in both `src/background.js` and `src/options.js` — when adding a new feature, update both, plus the corresponding UI block in `src/options.html`/`src/options.js` (a `.switch` toggle + optional fields, following the existing card markup).

Classic content scripts that gate a simple on/off feature (`disableAutoPlay.js`, `hideBroadcastButton.js`, and the panel init in `content.js`) do a lightweight one-off check instead of importing the full defaults:

```js
chrome.storage.local.get(['settings']).then(({ settings }) => {
  if (settings?.features?.<name>?.enabled === false) return; // default-on: undefined means enabled
  // ... run the feature
});
```

Follow this pattern for any new simple content-script toggle rather than pulling in `DEFAULT_SETTINGS`.

The extension icon has no `default_popup` (see `manifest.json`'s empty `action`), so `chrome.action.onClicked` in `background.js` opens the options page (`options_ui` in manifest, `open_in_tab: true`) instead.

### Live-monitor feature (background.js + soopLiveApi.js + liveMonitor.js)

This is the most involved subsystem. Key design points, in case they need to be extended:

- **All Soop API calls happen in `background.js`** (via `soopLiveApi.js`'s `isStreamerLive`/`getChannelBroad`, hitting `api-channel.sooplive.com`), never from content scripts — background/extension contexts get CORS-free fetches for `host_permissions` origins; content scripts don't (their fetch/XHR is bound by the *page's* origin for CORS, regardless of host_permissions). `soopLiveApi.js` is a minimal in-repo port of `GetChannelBroad` from the sibling project `../VOD-Master/src/.test/soop_api_standalone.js`; if more Soop API surface is needed later, that file is the source to port from (not a runtime dependency).
- **`chrome.alarms` (`liveCheck`, min. 1 minute — a Chrome-enforced floor)** drives periodic polling of registered streamers. `chrome.storage.session` holds the ephemeral `monitoredTabs: {tabId: streamerId}` map, which scopes "auto-managed" tabs. This is why `liveMonitor.js` always starts by asking background `liveMonitor:init` and does nothing if the answer is `monitored: false` — tabs the user opens manually are never touched.
- **The per-tick decision is level-triggered, not edge-triggered**: on every alarm tick, for each enabled streamer, the rule is simply "is live && has no open monitored tab" → open a tab. This single rule intentionally covers both the first time a stream goes live and recovery when a monitored tab was closed unexpectedly (crash, accidental close) while the stream was still live — no separate "previous state" bookkeeping needed.
- **Tabs are opened with a brief real focus, then handed back.** Soop's player does not appear to start streaming in a tab that's never been the active tab, so `runLiveCheck` creates the tab with `active: true`, remembers the previously-active tab, and `liveMonitor.js` detects true playback start (video `currentTime` advancing) and sends `liveMonitor:playbackStarted` so background can restore focus to the original tab (`FOCUS_RESTORE_FALLBACK_MS` is a safety timeout in case that signal never arrives). The video is muted (`muteVideo` in `liveMonitor.js`) as soon as it's found, precisely because this focus hand-off is real.
- **End-of-broadcast detection is deliberately two-step**, because "video stopped" is ambiguous (real end vs. network hiccup vs. being kicked): `liveMonitor.js` detects a stall/`ended`/`error` on the `<video>`, then asks background to re-check the live API on demand (`liveMonitor:checkStillLive`) rather than trusting the last polled state. Still live → `location.reload()` (capped by `MAX_RELOAD_ATTEMPTS`, counted in `sessionStorage` so the cap survives the reload). Actually offline → shows the countdown overlay and closes the tab (`liveMonitor:closeTab`) unless the user clicks "닫지 않기".

### VOD file listing (vodFileInfo.js)

The panel's file list comes from `getSoopVodInfo` (`station/video/a/view`, `files[]`); the download/upload flow separately calls `chk_download_auth.php`'s `szWork=LIST` (`FILE_LIST[]`) to get download-eligible entries. Both arrays carry a `file_order` field, but **`file_order` is not guaranteed to start at 1 or be contiguous per-VOD** — a VOD can legitimately have `files` numbered e.g. 3, 4, 5 (observed in practice) when earlier segments of the same broadcast belong to a different `title_no`. `buildFileMeta` therefore stores the real `fileOrder: Number(file.file_order)` per panel item, and both the download button and the upload title/attach-name lookup match `FILE_LIST` entries by `f.file_order === meta.fileOrder` — never by `meta.index + 1`. Using the array position instead of the real `file_order` was a real bug (found via VOD title_no 106472213, whose `files` were numbered 3/4/5): it silently failed to find a `FILE_LIST` entry for most items, and could even match the wrong file when an index+1 guess coincidentally hit a real `file_order`.

**"모두 다운로드&업로드" batch.** `runDownloadUploadAll` walks the files strictly one at a time: `downloadFile()` starts the download (returns `downloadId`), then `waitForDownloadOutcome(downloadId)` blocks until the download is confirmed finished, and only then `uploadFile()` runs (opens/reuses a Studio tab via `youtubeStudio:open`) before the loop moves on to the next file's download. `downloadFile`/`uploadFile` are the same functions the per-file buttons use (the buttons are thin wrappers), so both paths stay in sync. Completion is detected through storage, not a held-open message channel: background's `chrome.downloads.onChanged` listener writes `downloadOutcomes[downloadId] = {ok, name | error, recordedAt}` to `chrome.storage.local` (alongside the durable `downloadedFiles` name record), and the content script polls it (`DOWNLOAD_OUTCOME_POLL_MS`, up to `DOWNLOAD_WAIT_TIMEOUT_MS`) and deletes the entry it consumed — a service worker can die during a multi-GB download, but storage survives (same reasoning as `pendingDownloads`). Ordinary manual downloads never consume their outcome, so `pruneOldDownloadOutcomes` drops entries older than 24h on each write. Deliberate simplifications: the loop does **not** wait for the Studio-side automation (fill/save/close) of file *n* to finish before starting file *n+1*'s download — if that tab is still busy when file *n+1*'s upload starts, `tryReuseStudioTab` correctly refuses it and a new tab opens; a failed download is recorded on that file's status line and the batch continues with the next file rather than aborting; the summary counts "upload started", not "upload finished". All per-file buttons and the batch button are disabled while it runs. A red "배치 중단" button (visible only while running) sets a local `cancelled` flag: `waitForDownloadOutcome` takes a `shouldCancel` callback and returns `{cancelled:true}`, the in-flight download is cancelled via a `download:cancel` message (background calls `chrome.downloads.cancel`), the loop stops before starting any further file, and the summary reports how many files were left untouched. Uploads already started (Studio tabs) are not undone.

**The loop no longer downloads unconditionally.** Before calling `downloadFile()`, each iteration calls `checkAlreadyDownloaded(videoId, fileOrder)`, which asks background's `download:findExisting` handler whether that file order already has a usable local copy. Background doesn't just trust the `downloadedFiles[key]` record (which could point at a file the user since deleted outside the extension) — it re-verifies via `chrome.downloads.search({id: record.downloadId})` (calling `search` is what makes Chrome refresh the `exists` flag) and only reports `exists:true` if that download is `state:'complete'` and `exists !== false`. If it exists, the download step (and the wait-for-outcome step) is skipped entirely and the loop goes straight to `uploadFile()` — which already picks up the previously-recorded filename via `downloadedFiles[key].name` for Studio attach-matching, so no other change was needed there. If it doesn't exist (including "record present but file gone"), the file is downloaded exactly as before. This matters most for the VOD pipeline (below): a retried/resumed pipeline run, or a VOD whose files were partially downloaded before an interruption, won't blindly re-download files it already has.

### YouTube upload helper (vodFileInfo.js + background.js + youtubeStudio.js)

Uploading is done through **YouTube Studio's own uploader**, not the YouTube Data API — `videos.insert` (OAuth via `chrome.identity`) was tried and removed earlier: slower end-to-end than uploading in Studio directly, and videos uploaded via an unverified API project are locked private until audited. Don't reintroduce the API route without weighing that.

**background is a thin relay, not a queue owner.** `vodFileInfo.js`'s "유튜브에 업로드" button sends `{action:'studio:upload', title, description, fileNames, videoId, fileOrder}` to background. background merges in the saved options (`settings.features.vodFileInfo.*`) and forwards it to the Studio tab as `{action:'studio:newRequest', payload}` via `deliverStudioRequest()`, which uses the generic `ensureTabAt()`/`sendWithRetry()`/`waitForTabLoad()` helpers: if no Studio tab is tracked (`studioTabId`, `chrome.storage.session`), it opens `https://www.youtube.com/upload` and waits for the tab to finish loading before sending (a freshly created tab's content script may not have registered its message listener yet — `sendWithRetry` also retries a few times on top of that, and if sending still fails the tab is assumed dead and background opens a fresh one once more); if a tab is already tracked, it sends directly — there's no "is it busy" check. There is no `probe`/`restart` round-trip and no `studioUploadQueue` in background anymore — **the request queue lives inside `youtubeStudio.js` itself**, so background doesn't need to know whether the tab is busy, only that the message got there.

**`youtubeStudio.js`'s queue + two 1-second intervals — the only timers in the file.** `requestQueue` holds pending payloads (`studio:newRequest` pushes onto it). `runMainLoopTick()` pops one request and awaits `processRequest()` to full completion (success or give-up) before the next tick is allowed to pop another — never two requests in flight. `runDeletionLoopTick()` separately sweeps `deletionList` every tick (see below). Both run unconditionally from `init()`; there's no per-request timer setup/teardown.

**The 8-step sequence and its restart rule.** `processRequest()` loops `runRequestAttempt()`: 1) click "만들기", 2) click "동영상 업로드", 3) select the file, 4) fill title/description/not-for-kids, 5) select playlists, 6) select visibility, 7) click save, 8) close the completion popup. On failure, the restart point is one of three, tracked by two milestones (`fileSelected`, `saved`) that only ever flip from `false` to `true` across attempts for this request: before step 3 has ever succeeded, restart from step 1 (`cleanupStrayDialogs()` first closes any leftover dialog from the failed attempt, then the dialog is reopened from scratch); once step 3 has succeeded but step 7 hasn't, restart from step 4 (the dialog + attached file are still there); once step 7 (save) has ever succeeded, restart from step 8 **only** — retrying title/description/playlist/visibility/save would be pointless (the video is already saved to Studio) and actively wrong (the upload dialog's input fields are gone by then, so re-running step 4 would just fail immediately on "제목/설명 입력칸을 찾지 못함" every time). `closeCompletionPopup()` doesn't need a `dialog` reference — it searches `document` broadly — so step 8 alone needs no dialog lookup at all. Each request tracks `bestStepReached`/`stagnantRetries`: a restart that doesn't get further than the previous best increments `stagnantRetries` (reset to 0 the moment progress improves); once it exceeds `MAX_STAGNANT_RETRIES` (5), the request is abandoned — its remaining steps are skipped and this is **never reported as a failure** to `vodFileInfo.js`/`vodList.js` (it only shows in this tab's own panel/console) — and the whole tab enters manual-wait mode. If `saved` was already `true` at give-up time, the file genuinely made it into Studio even though the popup never closed, so `processRequest` still calls `addToDeletionList()` before giving up — otherwise a successfully uploaded file would silently never enter delete-after-upload tracking.

**Manual-wait mode.** `manualWaitMode = true` stops `runMainLoopTick()` from popping anything new. The tab hands back whatever was still queued (plus any request that arrives afterward, bounced the same way) via `{action:'studio:tabUnusable', leftoverRequests}`; background clears `studioTabId` so the *next* upload opens a brand-new tab, and re-delivers each leftover through the same `deliverStudioRequest()` path (so they land in that new tab). The broken tab itself is **left open**, not closed, so a human can finish whatever it was doing by hand.

**Waiting for folder permission is not a failure.** Step 3's `selectFile()` internally polls (every second) while the download folder isn't connected/granted yet, showing the banner's folder button — this never increments `stagnantRetries` and never times out, since it's waiting on a person, not failing. Once permission is there, it looks the file up by name (`buildNameMatchers`: exact name, Chrome's ` (n)` duplicate suffix, and the two ways illegal filename characters get replaced — `-` by this extension's/Soop's sanitizing, `_` by Chrome's own — never partial matches, since `_1.mp4` vs `_10.mp4` would otherwise collide) and attaches it via `DataTransfer` + `input`/`change` events. If Studio doesn't react (title/description boxes never appear) or the file genuinely isn't found despite having permission, *that* is a real, retry-counted step-3 failure. Chrome blocks the OS-default Downloads folder in the picker, hence the `downloadSubfolder` setting (relative to Chrome's download dir) — background applies it in `download:start`, and `findDownloadedFile()` also descends into that subfolder if a parent was connected. `download:start` runs the filename through `sanitizeFileName` first (so `chrome.downloads` doesn't reject it as invalid; the upload **title** keeps the unsanitized original) and records `pendingDownloads[downloadId]` in `chrome.storage.local` (service workers can die mid-download) — `chrome.downloads.onChanged` writes the actual saved basename to `downloadedFiles['{videoId}:{fileOrder}']`, which `vodFileInfo.js` passes (plus Soop's original `file_name`) as `fileNames`.

Beyond file attachment and title/description, step 4–6 apply the saved options (`youtubeNotForKids`/`youtubePlaylists`/`youtubeVisibility`, edited in the options page, carried in the payload's `options`): click the "not made for kids" radio, open the playlist dropdown and **wait for the account's playlists to actually load** (`waitForPlaylistRows` waits until rows appear and their count stops changing for `PLAYLIST_STABLE_MS`, then a short extra grace `PLAYLIST_ROW_GRACE_MS` per name for batches that arrive later), tick each configured playlist **by exact name** (never partial match), then jump to the visibility step and click the configured radio.

**Every click still goes through `confirmFound`/`waitForStable`, `CONFIRM_GAP_MS` (1s) apart, before being pressed** — unchanged from before. Studio is a heavily dynamic SPA where an element can satisfy a selector for one instant mid-transition, so a click target is always confirmed, waited out, and re-confirmed first:
- `confirmFound(getter, confirmGapMs)`: if `getter()` is falsy right now, returns `null` immediately (no cost for something that was never going to appear). If truthy, waits `confirmGapMs` and calls `getter()` again, returning that *second* call's (possibly fresh) reference only if still truthy.
- `waitForStable(getter, timeoutMs, ...)`: `waitFor`'s polling loop, but each candidate is run through `confirmFound` before being accepted.

The one deliberate exception remains `ensureChecked`'s own click — the caller already holds a confirmed reference, so it instead retries by checking the click's *effect* (`isChecked`).

**Deletion loop — one shared sweep instead of a per-upload watcher.** Every request that completes all 8 steps is pushed onto `deletionList` with `baselineRowCount`: a snapshot, taken **before the file is attached** (step 3), of how many Studio video-list rows already match this title. This is the same anti-false-positive technique the old design needed and for the same reason — Studio creates the row the instant a file is attached, well before save, so without a pre-attach snapshot a pre-existing same-titled row could be mistaken for the new upload. Each tick, per entry: skip if less than `MIN_DELAY_AFTER_SAVE_MS` (1 minute) has passed since it was added (same reasoning — give the real new row time to appear instead of matching a stale one right after save); otherwise take `rowsMatchingTitle(title)[0]` **only if** the current match count exceeds `baselineRowCount` (a genuinely new row appeared — `rowsMatchingTitle` unifies what used to be two separate functions, one counting, one finding-first, since both ultimately read the same title-matching row list); check whether its `.cell-description` visibly (never a hidden pre-rendered alternate — `isVisible`) reads exactly "업로드됨" (`isUploadMarkedDone`); once that's held for `UPLOAD_ROW_DONE_CONFIRM_MS` (5s, flicker guard), mark it ready. Ready + `autoDelete` on → `download:deleteUploaded` immediately; ready + off → the panel shows a manual delete button for it. An entry that can't be confirmed within `UPLOAD_ROW_DONE_TIMEOUT_MS` (6h) is dropped (logged, local file left alone — never deletes optimistically). Because the queue is strictly sequential within one tab, there's no more "does this watcher survive tab reuse" question — the sweep just walks whatever's in `deletionList`, regardless of which request added it, every tick.

**Debugging aid: row↔panel color matching.** Each `deletionList` entry gets a color from a fixed palette (cycling) the moment it's created. Every tick that finds its row, the row's title text is painted that color via `paintRow()` (and cleared via `unpaintRow()` the moment the row can't be found, or once the entry is removed); the panel's own entry for it shows a swatch in the same color. This makes a row-matching mismatch — exactly the class of bug that bit the old per-upload-watcher design — visible at a glance instead of only discoverable by reading logs.

**Panel/console split.** The banner shows only the current request's step progress (`[요청 #N] 3/8 파일 선택`) and failures, plus the full deletion list (every entry + its manual-delete button when applicable) — everything else is `console.log`/`console.warn` only. The banner is self-healing **structurally**, not by convention: `setStatusText`, `setFolderPromptVisible`, and `renderDeletionPanel` all call `ensureBanner()` as their first line, which recreates the host from scratch if the cached `bannerHostEl.isConnected` is false — there's no "remember to call this first" rule for future code to forget.

**What no longer exists, and why dropping it is safe.** The old tab-reuse decision state machine (`isReusable`/`dialogEverSeen`/`explicitlyIdle`/`reuseBlockedUntil`/`runPhase`/`currentRunId`, plus the `youtubeStudio:probe`/`:restart` messages and `watchForSave`'s click-listener/`runSavedAt` map) existed to answer one question: "can background hand this *already-open* tab a brand-new upload right now?" That question doesn't exist anymore — background never asks, it just delivers to whatever tab is tracked, and the tab's own queue (not background) decides when the next request may start, which is strictly after the previous one finished (success or manual-wait). `clickSaveButton()` *is* the save click, so there's no separate click-detection listener needed to know when saving happened.

None of this has been run end-to-end in a real browser yet (same caveat as always) — the Studio selectors (`*_SELECTORS`/`*_SELECTOR`/`VISIBILITY_*` at the top of `youtubeStudio.js`) were written from memory and may need fixing against the live DOM if auto-fill stops working; the banner has no copy-title/description fallback buttons anymore (if automation can't finish, the tab sits in manual-wait with the dialog open for the user to finish directly in Studio).

### 다시보기 목록의 유튜브 업로드 여부 판별 (vodList.js + youtubeVideos.js + youtubeMatch.js)

`www.sooplive.com/station/*/vod*` 목록 페이지의 "유튜브 업로드 여부 확인" 버튼이 `vodUpload:match`를 background에 보낸다. 판별 근거는 로컬 기록이 아니라 **내 채널의 실제 업로드 영상**이다: 영상 **설명의 Soop 링크(`sooplive.com/player/{titleNo}`)**로 어느 다시보기인지, **제목의 `[날짜 (n/max)]`**(파일이 하나면 `[날짜]` → 1/1)로 몇 번째 파일인지 맞춘다(`youtubeMatch.js`, 순수 함수). n은 `files` 배열 순서(1부터)이지 `file_order`가 아니다. 영상 목록은 `studio.youtube.com` 탭의 content script(`youtubeVideos.js`)가 Studio 내부 API `creator/list_creator_videos`를 SAPISIDHASH로 호출해 가져오며(열린 Studio 탭이 없으면 background가 잠깐 열었다 닫는다), 이 API의 요청/응답 형식은 기억에 의존해 쓴 것이라 **브라우저에서 검증되지 않았다** — 실패 시 에러에 응답 본문 일부가 담긴다. 결과는 콘솔과 `private-extension:vod-match` window 이벤트(`{pending, uploaded, all}`)로도 나가며, 아래 파이프라인이 이어받는다.

### 다시보기 배치 — 목록 페이지 → 플레이어 페이지를 잇는 자동화 (background.js + vodList.js + vodFileInfo.js)

목록 페이지의 "모두 업로드" 버튼이 시작하는, 여러 다시보기를 무인으로 순서대로 처리하는 기능. 예전에는 background.js가 `vodPipeline`이라는 상태 머신(`{running, queue, current, done, failed, paused, throttled, hasFailures}`)을 `chrome.storage.session`에 들고 모든 조율(언제 다음 다시보기로 넘어갈지, 일시정지, 디스크 스로틀까지)을 책임졌지만, 지금은 **큐를 vodList.js 자신이 들고 돌리고 background는 플레이어 탭을 열어주는 얇은 중계자일 뿐이다** — 상태 저장소도, 일시정지/스로틀 개념도 background에는 없다.

**흐름.** (1) `vodList.js`가 `checkMatch()`로 미업로드 다시보기들을 추려 자기 모듈 변수(`batchQueue`)에 담고, 파일 단위 업로드 여부(`vod.files[].uploaded`)로 다시보기별 `skipFileOrders`도 같이 계산해둔다. (2) 큐에서 하나씩 꺼내 `{action:'vodBatch:start', videoId, skipFileOrders}`를 background로 보낸다 — background는 플레이어 탭(`playerTabId`, 하나만 두고 재사용 — Studio 탭과 같은 이유)을 그 videoId로 열거나 이동시키고 로드가 끝나길 기다린 뒤(`ensureTabAt`) `{action:'vodBatch:begin', videoId, skipFileOrders}`를 그 탭에 전달하며, 완료를 돌려줄 곳을 기억해두려고 `vodBatchRequest`(요청한 vodList.js 탭 id + videoId, 세션 스토리지)도 같이 기록한다. (3) `vodFileInfo.js`가 `vodBatch:begin`을 받으면(패널 로딩보다 먼저 도착할 수 있어 `pendingBatchPayload`에 잠깐 보관했다가 `latestRenderResult`가 준비되는 대로 시작) 패널을 펼치고 영상 재생을 멈춘 뒤, 버튼 클릭 없이 "모두 다운로드&업로드"(`runBatch(skipFileOrders)`)를 그대로 돌린다. (4) **로컬 단계(다운로드 + Studio 업로드 요청 제출)가 끝나는 즉시** — Studio가 실제 전송을 끝냈는지는 기다리지 않고 — `{action:'vodBatch:complete', videoId, successOrders, failOrders, cancelled}`를 background로 보낸다. (5) background는 `failOrders`가 있으면 파일별로 기록/알림(`recordPipelineFailure`)을 남기고, 기억해둔 요청자 탭(vodList.js)에 그대로 전달한다. (6) vodList.js가 결과를 누적해 보여주고 큐의 다음 항목을 이어서 시작한다 — 플레이어 탭은 새로 열지 않고 그대로 재사용(URL만 이동)한다.

**왜 "Studio 확인"을 더 이상 기다리지 않는가.** 예전엔 `confirmedFileOrders`/`isCurrentVodSettled`/`canFastForwardVod` 같은 장치로 "지금까지 실패가 없었으면 로컬 단계만 끝나도 지름길로 다음 다시보기로 넘어간다"는 최적화를 별도로 두고 있었다. 지금은 그 지름길이 **기본 동작 자체**다 — `vodBatch:complete`가 로컬 단계 종료 즉시 발사되므로, Studio 쪽 업로드 확인("업로드됨" 텍스트 확인)은 이제 전적으로 `youtubeStudio.js`의 삭제 담당 Loop 내부 관심사일 뿐, 다시보기 배치의 진행 여부와는 완전히 무관하다. 이 덕분에 "파일 하나하나의 Studio 확인 신호를 배치 진행에 쓰는" 메시지(`vodPipeline:fileConfirmed`) 자체가 통째로 사라졌다.

**일시정지 기능은 삭제했다(사용자 요청).** "진행 중인 다운로드/업로드는 그대로 두고 다음 단계부터만 멈춘다"는 일시정지/재개 버튼과 그 인프라(`state.paused`/`state.throttled`/`setPipelinePauseFlag`)는 전부 제거했다. 디스크 공간 보호를 위한 자동 스로틀(삭제 대기 파일이 너무 쌓이면 새 업로드 처리를 잠깐 멈추는 것)은 기능 자체는 남아 있지만, **다른 페이지에는 전혀 노출하지 않고 `youtubeStudio.js`의 MainLoop 안에서만** 판단한다 — 삭제 대상 리스트 중 자동 삭제 대상(`!manual`) 개수가 `PENDING_DELETION_THROTTLE`(10) 이상이면 그 틱은 업로드 큐에서 다음 요청을 꺼내지 않고 건너뛸 뿐이다. vodList.js/vodFileInfo.js 입장에서는 그냥 "아직 처리가 안 끝난 상태"로 보일 뿐 — 일시정지라는 개념 자체를 모른다.

**안전망.** vodList.js는 `vodBatch:start` 응답 후 `VOD_BATCH_TIMEOUT_MS`(12시간) 안에 `vodBatch:complete`가 안 오면 그 다시보기를 실패로 치고 다음으로 넘어간다(응답의 `videoId`가 `batchCurrentVideoId`와 다르면 이미 시간 초과 등으로 처리된 옛 응답이라 무시 — 늦게 온 응답이 다음 다시보기의 결과를 덮어쓰지 않는다). 플레이어 탭이 사용자에 의해 직접 닫히면 background의 `chrome.tabs.onRemoved`가 `playerTabId`를 비우고, 기다리고 있던 요청자 탭에 `cancelled:true`로 완료를 대신 보내 영원히 기다리지 않게 한다. "중단" 버튼은 vodList.js의 남은 큐(`batchQueue`)를 비우고(더 이상 다음 다시보기를 시작하지 않음) `vodBatch:cancel`을 보내 지금 돌고 있는 배치만 즉시 멈춘다(이미 시작된 파일의 다운로드/업로드는 끝까지 — 기존 "배치 중단" 버튼과 동일 정책).

**복원력은 의도적으로 없다.** vodList.js든 플레이어 탭이든 배치 도중 새로고침되면 진행 상황은 그냥 끊긴다 — 둘 다 모듈 메모리에만 큐/상태를 들고 있고 background에 영구 저장하지 않는다(사용자가 다시 시작해야 함). 단순함을 우선한 의도적인 선택이다.

이 배치 흐름(탭 간 메시지, 실제 타이밍, 데스크톱 알림이 실제로 뜨는지)은 아직 실제 브라우저에서 처음부터 끝까지 돌려보지 않았다 — 기존과 같은 캐비엇.

### Legacy/unused files

`src/popup.html`, `popup.js`, `styles.css`, `soopHandler.js`, `taskRunner.js`, `dummy.js` are **not referenced by `manifest.json`** — superseded by the in-page panel (`content.js`) and the options page. Don't extend them and don't assume they run; they're kept around but dead.

## Conventions

- UI copy, comments, and commit messages are in Korean; match that when editing existing files.
- Logging in the live-monitor subsystem is tagged `[LiveMonitor]` in both `background.js` and `liveMonitor.js` — keep using that tag for related additions so logs stay filterable.
- In `youtubeStudio.js`, every log line tied to a specific upload request is tagged `[YoutubeStudio] [요청 #N]` (`N` from `requestSeq`, incremented once per `processRequest()` call) rather than the bare `LOG_TAG`. Unlike the old tab-reuse design, this isn't load-bearing for correctness anymore — MainLoop awaits each request to full completion before starting the next, so there's never more than one request's work in flight to disambiguate — it's purely a log-reading convenience for telling consecutive requests' lines apart in the console.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"나만의 SOOP 확프" — a Manifest V3 Chrome extension for Soop (sooplive.com, formerly AfreecaTV). No bundler, no framework, no package.json: every file in `src/` is a plain script loaded directly by `manifest.json`. There is no build step.

## Commands

There is no build/lint/test tooling in this repo. Development loop:

- **Syntax-check a file after editing it**: `node --check src/<file>.js` (works for both classic scripts and the ES-module `background.js`/`soopLiveApi.js` on modern Node).
- **Validate manifest.json**: `node -e "JSON.parse(require('fs').readFileSync('manifest.json','utf8'))"`.
- **Manual test**: load unpacked at `chrome://extensions` (enable Developer mode → "압축해제된 확장 프로그램을 로드합니다" → select the repo root), then reload the extension after each change.
- **Background logs**: `chrome://extensions` → this extension's "service worker" link opens its DevTools console.
- **Content script logs** (panel, live monitor, etc.): open DevTools on the relevant `play.sooplive.com` tab.

## Architecture

### No bundler ⇒ shared JS world per content_scripts entry

Content scripts listed together in one `content_scripts` entry of `manifest.json` execute in the same isolated-world JS context on that page, so top-level `const`/`function` names in one file are visible to the others in the same entry and can collide. `content.js` and `songSearch.js` rely on this (deliberately share globals like `SongSearch`). Scripts that don't need to share state (`disableAutoPlay.js`, `hideBroadcastButton.js`, `liveMonitor.js`) are wrapped in an IIFE — keep doing this for new standalone content scripts.

`background.js` is the only ES module (`"type": "module"` in manifest) and is the only place that can `import` from `soopLiveApi.js`.

### Settings: one storage key, feature-gated

All configuration lives under a single `chrome.storage.local` key, `settings`, shaped as `{ features: { <featureName>: {...} } }`. Each feature object has at minimum `enabled: boolean`. This schema is intentionally duplicated (not shared via an imported module) as `DEFAULT_SETTINGS` in both `src/background.js` and `src/options.js` — when adding a new feature, update both, plus the corresponding UI block in `src/options.html`/`src/options.js` (a `.switch` toggle + optional fields, following the existing card markup).

Classic content scripts that gate a simple on/off feature (`disableAutoPlay.js`, `hideBroadcastButton.js`, and the panel init in `content.js`) do a lightweight one-off check instead of importing the full defaults:

```js
chrome.storage.local.get(['settings']).then(({ settings }) => {
  if (settings?.features?.<name>?.enabled === false) return; // default-on: undefined means enabled
  // ... run the feature
});
```

Follow this pattern for any new simple content-script toggle rather than pulling in `DEFAULT_SETTINGS`.

The extension icon has no `default_popup` (see `manifest.json`'s empty `action`), so `chrome.action.onClicked` in `background.js` opens the options page (`options_ui` in manifest, `open_in_tab: true`) instead.

### Live-monitor feature (background.js + soopLiveApi.js + liveMonitor.js)

This is the most involved subsystem. Key design points, in case they need to be extended:

- **All Soop API calls happen in `background.js`** (via `soopLiveApi.js`'s `isStreamerLive`/`getChannelBroad`, hitting `api-channel.sooplive.com`), never from content scripts — background/extension contexts get CORS-free fetches for `host_permissions` origins; content scripts don't (their fetch/XHR is bound by the *page's* origin for CORS, regardless of host_permissions). `soopLiveApi.js` is a minimal in-repo port of `GetChannelBroad` from the sibling project `../VOD-Master/src/.test/soop_api_standalone.js`; if more Soop API surface is needed later, that file is the source to port from (not a runtime dependency).
- **`chrome.alarms` (`liveCheck`, min. 1 minute — a Chrome-enforced floor)** drives periodic polling of registered streamers. `chrome.storage.session` holds the ephemeral `monitoredTabs: {tabId: streamerId}` map, which scopes "auto-managed" tabs. This is why `liveMonitor.js` always starts by asking background `liveMonitor:init` and does nothing if the answer is `monitored: false` — tabs the user opens manually are never touched.
- **The per-tick decision is level-triggered, not edge-triggered**: on every alarm tick, for each enabled streamer, the rule is simply "is live && has no open monitored tab" → open a tab. This single rule intentionally covers both the first time a stream goes live and recovery when a monitored tab was closed unexpectedly (crash, accidental close) while the stream was still live — no separate "previous state" bookkeeping needed.
- **Tabs are opened with a brief real focus, then handed back.** Soop's player does not appear to start streaming in a tab that's never been the active tab, so `runLiveCheck` creates the tab with `active: true`, remembers the previously-active tab, and `liveMonitor.js` detects true playback start (video `currentTime` advancing) and sends `liveMonitor:playbackStarted` so background can restore focus to the original tab (`FOCUS_RESTORE_FALLBACK_MS` is a safety timeout in case that signal never arrives). The video is muted (`muteVideo` in `liveMonitor.js`) as soon as it's found, precisely because this focus hand-off is real.
- **End-of-broadcast detection is deliberately two-step**, because "video stopped" is ambiguous (real end vs. network hiccup vs. being kicked): `liveMonitor.js` detects a stall/`ended`/`error` on the `<video>`, then asks background to re-check the live API on demand (`liveMonitor:checkStillLive`) rather than trusting the last polled state. Still live → `location.reload()` (capped by `MAX_RELOAD_ATTEMPTS`, counted in `sessionStorage` so the cap survives the reload). Actually offline → shows the countdown overlay and closes the tab (`liveMonitor:closeTab`) unless the user clicks "닫지 않기".

### VOD file listing (vodFileInfo.js)

The panel's file list comes from `getSoopVodInfo` (`station/video/a/view`, `files[]`); the download/upload flow separately calls `chk_download_auth.php`'s `szWork=LIST` (`FILE_LIST[]`) to get download-eligible entries. Both arrays carry a `file_order` field, but **`file_order` is not guaranteed to start at 1 or be contiguous per-VOD** — a VOD can legitimately have `files` numbered e.g. 3, 4, 5 (observed in practice) when earlier segments of the same broadcast belong to a different `title_no`. `buildFileMeta` therefore stores the real `fileOrder: Number(file.file_order)` per panel item, and both the download button and the upload title/attach-name lookup match `FILE_LIST` entries by `f.file_order === meta.fileOrder` — never by `meta.index + 1`. Using the array position instead of the real `file_order` was a real bug (found via VOD title_no 106472213, whose `files` were numbered 3/4/5): it silently failed to find a `FILE_LIST` entry for most items, and could even match the wrong file when an index+1 guess coincidentally hit a real `file_order`.

**"모두 다운로드&업로드" batch.** `runDownloadUploadAll` walks the files strictly one at a time: `downloadFile()` starts the download (returns `downloadId`), then `waitForDownloadOutcome(downloadId)` blocks until the download is confirmed finished, and only then `uploadFile()` runs (opens/reuses a Studio tab via `youtubeStudio:open`) before the loop moves on to the next file's download. `downloadFile`/`uploadFile` are the same functions the per-file buttons use (the buttons are thin wrappers), so both paths stay in sync. Completion is detected through storage, not a held-open message channel: background's `chrome.downloads.onChanged` listener writes `downloadOutcomes[downloadId] = {ok, name | error, recordedAt}` to `chrome.storage.local` (alongside the durable `downloadedFiles` name record), and the content script polls it (`DOWNLOAD_OUTCOME_POLL_MS`, up to `DOWNLOAD_WAIT_TIMEOUT_MS`) and deletes the entry it consumed — a service worker can die during a multi-GB download, but storage survives (same reasoning as `pendingDownloads`). Ordinary manual downloads never consume their outcome, so `pruneOldDownloadOutcomes` drops entries older than 24h on each write. Deliberate simplifications: the loop does **not** wait for the Studio-side automation (fill/save/close) of file *n* to finish before starting file *n+1*'s download — if that tab is still busy when file *n+1*'s upload starts, `tryReuseStudioTab` correctly refuses it and a new tab opens; a failed download is recorded on that file's status line and the batch continues with the next file rather than aborting; the summary counts "upload started", not "upload finished". All per-file buttons and the batch button are disabled while it runs. A red "배치 중단" button (visible only while running) sets a local `cancelled` flag: `waitForDownloadOutcome` takes a `shouldCancel` callback and returns `{cancelled:true}`, the in-flight download is cancelled via a `download:cancel` message (background calls `chrome.downloads.cancel`), the loop stops before starting any further file, and the summary reports how many files were left untouched. Uploads already started (Studio tabs) are not undone.

**The loop no longer downloads unconditionally.** Before calling `downloadFile()`, each iteration calls `checkAlreadyDownloaded(videoId, fileOrder)`, which asks background's `download:findExisting` handler whether that file order already has a usable local copy. Background doesn't just trust the `downloadedFiles[key]` record (which could point at a file the user since deleted outside the extension) — it re-verifies via `chrome.downloads.search({id: record.downloadId})` (calling `search` is what makes Chrome refresh the `exists` flag) and only reports `exists:true` if that download is `state:'complete'` and `exists !== false`. If it exists, the download step (and the wait-for-outcome step) is skipped entirely and the loop goes straight to `uploadFile()` — which already picks up the previously-recorded filename via `downloadedFiles[key].name` for Studio attach-matching, so no other change was needed there. If it doesn't exist (including "record present but file gone"), the file is downloaded exactly as before. This matters most for the VOD pipeline (below): a retried/resumed pipeline run, or a VOD whose files were partially downloaded before an interruption, won't blindly re-download files it already has.

### YouTube upload helper (vodFileInfo.js + background.js + youtubeStudio.js)

Uploading is done through **YouTube Studio's own uploader**, not the YouTube Data API. An earlier version used `videos.insert` (OAuth via `chrome.identity`, resumable upload streamed from the content script through background) and was removed: in practice it was noticeably slower end-to-end than uploading in Studio directly (both the transfer and the post-upload processing/checks, as observed), and per YouTube's API policy videos uploaded via `videos.insert` from an unverified API project are locked to private until the project passes an audit. Don't reintroduce the API route without weighing that.

Flow: the "유튜브에 업로드" button in `vodFileInfo.js` sends `{action:'youtubeStudio:open', title, description}` to background, which opens `https://www.youtube.com/upload` (redirects into Studio's upload dialog) in a new tab and stores the title/description in `chrome.storage.session` under `pendingStudioUploads[tabId]` (per-tab, so several upload tabs opened back-to-back don't get mixed up; cleaned on `tabs.onRemoved`). `youtubeStudio.js` (content script on `studio.youtube.com`) asks `youtubeStudio:init` and does nothing unless the answer is `pending: true` — same "only touch tabs we opened" gate as `liveMonitor.js`. It then polls for the title/description boxes **inside `ytcp-uploads-dialog` only** (the same boxes exist on the edit page of already-uploaded videos, so unscoped filling could overwrite a real video's title), fills them via `execCommand` (plain value assignment isn't picked up by Studio's Polymer bindings) and re-verifies a few times because Studio also auto-fills the title from the filename after the box appears. The file itself can't be handed over as bytes — `chrome.runtime` messaging is JSON-only (a `File` arrives with `size` undefined and an `ArrayBuffer` as `{}`; base64 strings are the only way to move bytes through it) — and a path string can't fill an `<input type="file">`. The working route is the File System Access API: `youtubeStudio.js` shows a banner button (a folder picker needs a user click) that lets the user grant the download folder once; the `FileSystemDirectoryHandle` is kept in the **Studio page origin's** IndexedDB (a handle can't cross between the extension's own pages and a content script's page). Then `tryAttach()` finds the file by exact name (`buildNameMatchers`: the name, Chrome's ` (n)` duplicate suffix, and Windows-illegal characters replaced by `-` (what `sanitizeFileName` in background and Soop's official download do) or `_` (Chrome's own sanitizing) — never partial matches, since `_1.mp4` vs `_10.mp4` would otherwise collide), builds a `File` from the handle, puts it into the dialog's file input via `DataTransfer` and dispatches `input`/`change`. Failure at any point (no permission, file not found, Studio not reacting) falls back to the user picking the mp4 manually. Chrome blocks the OS-default Downloads folder itself in the picker, hence the `downloadSubfolder` setting (relative to Chrome's download dir; `chrome.downloads` only accepts relative paths) — background applies it in `download:start`, and `findDownloadedFile()` also descends into that subfolder if a parent was connected. To match the file that was *actually* saved (Chrome sanitizes names and appends ` (1)` on duplicates), `download:start` first runs the filename through `sanitizeFileName` (illegal characters → `-`; unsanitized names made `chrome.downloads` fail with an invalid-filename error, while the upload **title** keeps the original unsanitized `file_name`), then records `pendingDownloads[downloadId]` in `chrome.storage.local` (not memory — the service worker can be killed during a long download) and `chrome.downloads.onChanged` writes the final basename to `downloadedFiles['{videoId}:{fileOrder}']` on completion; `vodFileInfo.js` passes that (plus Soop's original `file_name`) as `fileNames` to `youtubeStudio:open`. Beyond file attachment and title/description it also applies the saved options `settings.features.vodFileInfo.{youtubeNotForKids, youtubePlaylists, youtubeVisibility}` (edited in the options page; background passes them in the `youtubeStudio:init` response so defaults stay in one place): click the "not made for kids" radio, open the playlist dropdown, **wait for the account's playlists to actually load** (the popup opens empty and fills asynchronously — `waitForPlaylistRows` waits until rows appear and their count stops changing for `PLAYLIST_STABLE_MS`, and each name then gets a short extra grace `PLAYLIST_ROW_GRACE_MS` for batches that arrive later than that window; ticking immediately made every name "not found"), and tick each configured playlist **by exact name** (multi-select; no partial matching, so a similarly named playlist is never picked silently), then jump to the visibility step and click the configured radio. Each step runs independently via `safely()` — one failing doesn't block the others — and the banner shows ✓/✗ per step.

**Auto-save (toward full automation).** If every step above succeeds (`results.every(r => r.ok)`), `autoSaveAndClose()` clicks the save button (`DONE_BUTTON_SELECTOR`, `#done-button` — confirmed working) itself instead of waiting for the user, then polls (`findSaveCompletionCloseButton`, up to `SAVE_PROCESSING_TIMEOUT_MS`) for the "닫기"/"Close" button that appears afterward and clicks that too. If any earlier step failed, save is never attempted and the dialog is left for the user, same as before. The close button was confirmed by hand as a plain `<button aria-label="닫기">` with no id (`DIALOG_CLOSE_BUTTON_SELECTORS` tries `button[aria-label="닫기"]`/`"Close"` first, then falls back to text match and the older `#close-button` guess) — but **its container isn't scoped** to `UPLOAD_DIALOG_SELECTOR`/`SHARE_DIALOG_SELECTOR` the way every other step's lookup is, because that container tag is itself unconfirmed; `findSaveCompletionCloseButton`/`findVisibleButtonByText` instead search the whole `document` for a *visible* match (`findVisible`/`isVisible`, the same visibility-first approach as the "만들기" button and menu item). This is deliberately looser than the rest of the file's dialog-scoped selectors — acceptable here since it only runs in the few seconds right after our own scripted save click. If auto-save or the close click still doesn't work, check the console for `[YoutubeStudio] 저장 버튼(...)을 찾지 못함` / `완료 화면의 닫기 버튼을 찾지 못함`. `watchForSave`'s click listener on the dialog catches the scripted save click the same way it catches a manual one, so `runPhase` still flips to `'saved'` and tab reuse (`isReusable()`) keeps working unchanged.

**Every programmatic click in `youtubeStudio.js` requires the target to be confirmed twice, `CONFIRM_GAP_MS` (1s) apart, before it's pressed.** Studio is a heavily dynamic SPA — an element can satisfy a selector for one instant while mid-transition (about to be replaced, about to move, about to detach) and clicking on that instant risks pressing the wrong thing or a stale reference. Two helpers enforce this uniformly, and by convention **no code clicks anything in the Studio page without going through one of them first**:
- `confirmFound(getter, confirmGapMs = CONFIRM_GAP_MS)`: if `getter()` is falsy right now, returns `null` immediately (no wait — an element that was never going to appear shouldn't cost a delay). If truthy, waits `confirmGapMs` and calls `getter()` again, returning that *second* call's result (a fresh reference, in case the DOM node was swapped) only if it's still truthy; otherwise `null` (the first hit was a flicker, not a real state).
- `waitForStable(getter, timeoutMs, intervalMs = 200, confirmGapMs = CONFIRM_GAP_MS)`: `waitFor`'s polling loop, but each "found" candidate is run through `confirmFound` before being accepted — a flicker just continues the polling loop with whatever time remains under `timeoutMs`, rather than either accepting the flicker or giving up.

Every existing "detect then click" site was converted: `closeFinishedDialog`, `openUploadDialog`'s "만들기"/"동영상 업로드" clicks, `autoSaveAndClose`'s save-button and completion-popup-close-button clicks, `selectNotForKids`, `selectPlaylists`'s dropdown-trigger/per-row-checkbox/done-button clicks, and `selectVisibility`'s step-badge/next-button/radio/return-to-step clicks. The one deliberate exception is `ensureChecked`'s own `el.click()`/`inner.click()` — by the time it's called, `el` is already a specific reference the caller obtained via `confirmFound`/`waitForStable`, so re-confirming *presence* again would be redundant; `ensureChecked` instead retries by checking the click's *effect* (`isChecked`), a different, already-existing concern. This replaced the old bespoke `CLOSE_BUTTON_CLICK_DELAY_MS` (a fixed 2s sleep before clicking the completion popup's close button, motivated by the same "don't click too eagerly" concern) — `waitForStable`'s built-in confirm gap now serves that exact purpose generically, so the constant was removed. `autoSaveAndClose` also now sets `reuseBlockedUntil = Infinity` right when the save button is clicked (previously only once the close button had already been found), closing a small pre-existing gap where `isReusable()`'s dialog-still-open branch (`runPhase === 'saved'` with the dialog element still present) could theoretically call a tab reusable before `autoSaveAndClose` even got to searching for the close button.

**Row-confirmation after the close-button click, and why `isReusable()` needs its own gate for the whole save→close→confirm sequence.** Clicking the completion popup's close button too eagerly — and, worse, letting this tab be reused for the next upload too eagerly afterward — was suspected of causing Studio's video list row to not be fully updated yet when the next automation run started touching it. The pre-click side of this is now handled generically by `waitForStable`/`confirmFound` (previous section) rather than a bespoke sleep. What's specific to the close button is what happens *after* the click: instead of any fixed delay, the tab is only released once a **new** row for this upload's title has actually appeared in Studio's video list, via `countRowsMatchingTitle(currentTitle)` compared against a baseline (see `matchingRowsAtRunStart` below for exactly when that baseline is taken and why), polled (`waitFor(..., UPLOAD_ROW_APPEAR_TIMEOUT_MS, UPLOAD_ROW_POLL_MS)`) after the click until the count goes strictly above that baseline, or the timeout is hit (in which case it just proceeds anyway, logging a warning — never blocks the tab forever). Comparing counts rather than "does any matching row exist" is deliberate: a same-titled row could already exist from an earlier attempt, and `findRowByTitle`'s "first match" semantics would satisfy that check instantly without proving the *new* upload's row actually landed — `countRowsMatchingTitle` (a sibling of `findRowByTitle`, used only here) closes that gap by requiring the count to *increase*. The tricky part with timing this correctly: `isReusable()` already declares a tab reusable as soon as `runPhase === 'saved'` (set the instant the *save* button was clicked, well before `autoSaveAndClose` even gets to finding/clicking the close button) — so merely delaying `notifyBecameIdle()` wouldn't have been enough, since an independent trigger (the periodic `liveCheck` alarm, or another `youtubeStudio:open` arriving from elsewhere) could still probe `isReusable()` and reuse the tab mid-wait. The fix is a module-level `reuseBlockedUntil` timestamp, checked as the very first line of `isReusable()` (`if (Date.now() < reuseBlockedUntil) return false;`, overriding every other condition including `explicitlyIdle`): it's set to `Infinity` right when the save button is clicked (covering the entire search-for-close-button → click-it → confirm-new-row sequence) and only set to `Date.now()` once the row-count check settles (found or timed out) — so no external trigger can reuse this tab at any point in that whole window, regardless of `runPhase`. It's reset to `0` in `beginRun()` so a new run isn't blocked by a previous run's stale value. This gate is scoped specifically to `autoSaveAndClose`'s own save/close flow; it does not apply to `closeFinishedDialog` (the separate, already-scoped cleanup click `restartInThisTab` does on a leftover dialog when starting a genuinely new upload in this tab).

**A real bug: the count baseline used to be taken too late, so the "new row" check could never succeed.** The baseline (`matchingRowsAtRunStart`, a module var) must be snapshotted **before the file is attached**, not right before the close-button click — Studio creates the row for a title as soon as the file attaches (well before title/description are even filled, let alone before save/close), so by the time execution reaches the close-button click, the current upload's *own* row already exists and is already counted. A baseline taken at that point can therefore never be exceeded, and `autoSaveAndClose` would wait out the full `UPLOAD_ROW_APPEAR_TIMEOUT_MS` (3 minutes) and log `저장 후 동영상 목록에 새 행이 추가된 것을 확인하지 못함` on **every single upload**, not occasionally — this was confirmed as the cause after a user reported the warning firing for every file, and was previously masked because the code still "proceeded anyway" after the timeout rather than failing outright, so uploads kept working, just 3 minutes slower than necessary each. The fix: `beginRun(payload)` takes the snapshot itself, immediately after setting `currentTitle`, i.e. before `tryAttach()` ever runs — `matchingRowsAtRunStart = countRowsMatchingTitle(currentTitle);`. `autoSaveAndClose(dialog, runId, results)` then captures that module value into a local `matchingRowsBeforeThisRun` at its very start (before any of its own `await`s), so a tab reuse that overwrites the module var for a *later* run mid-flight can't corrupt an in-progress `autoSaveAndClose`'s comparison.

**Delete local file after upload confirmed (opt-in, default off).** `settings.features.vodFileInfo.deleteLocalFileAfterUpload` (options page, red-flagged warning text, default `false` since this is destructive) flows through `buildStudioPayload`'s `options.deleteAfterUpload` and `youtubeStudio:open`'s `videoId`/`fileOrder` (added alongside `title`/`description`/`fileNames`; `vodFileInfo.js`'s `uploadFile()` always sends `meta.fileOrder`, the real Soop `file_order`, regardless of whether the Studio-side attach later succeeds). In `youtubeStudio.js`, `watchUploadAndDelete(runId, title, shouldDelete)` is started from inside `tryAttach()`'s success branch — i.e. only when **our own automatic attach** put a specific known local file into the input, never when the user picked a file manually (we'd have no way to know if that matches `videoId`/`fileOrder`).

**A real bug: the watcher used to not even start when both `deleteAfterUpload` and the VOD pipeline were off — silently breaking the manual-delete-button and pending-file panel for ordinary manual uploads.** `tryAttach()` used to gate the call to `watchUploadAndDelete` behind `(currentOptions.deleteAfterUpload || currentOptions.pipeline)`. That made sense when the watcher's only job was auto-deletion, but once the manual "지금 로컬 파일 삭제" button and the pending-deletions panel (below) were added — both meant to work specifically *when auto-delete is off* — this condition became a bug: a plain manual "유튜브에 업로드" click, with auto-delete off and outside the VOD pipeline, never started the watcher at all, so the upload was never confirmed, the manual delete button never appeared (it just sat `hidden`), and the file never showed up in the pending-deletions panel. This was reported by a user who found the button element in the DOM via `querySelector` but it stayed `hidden` forever. Fixed by removing the gate entirely: `tryAttach()` now always calls `watchUploadAndDelete(runId, currentTitle, currentOptions.deleteAfterUpload)` whenever the file was successfully auto-attached and `currentVideoId`/`currentFileOrder` are known — `shouldDelete` (still `currentOptions.deleteAfterUpload`) is what the watcher itself uses internally to decide auto-delete vs. manual-offer-only, not whether to watch at all.

**Pending-deletions panel now also tracks manual-delete files, not just auto-delete files.** Previously `notifyPendingDeletion` was only called when `shouldDelete` was true, so a file the user must delete manually never appeared in the Studio banner's collapsible "삭제 대기 중인 파일" list — there was no way to see, days later, which confirmed-uploaded files were still sitting on disk unless the single (one-at-a-time) manual-delete button happened to still be showing it. Now `watchUploadAndDelete`'s `!shouldDelete` branch also calls `notifyPendingDeletion(videoId, fileOrder, title, true, true)` (the new 5th arg, `manual`) right when "업로드됨" is confirmed and the manual button is offered — this is later than the auto-delete path's own `notifyPendingDeletion(..., true, false)` call (sent right at the start of the watch, before confirmation), since only once confirmed do we actually know the file needs deleting. The entry is only cleared (`pending:false`) when the user actually clicks the manual delete button and it succeeds (`onDeleteNowButtonClick`, not `watchUploadAndDelete`'s `finally` — the `finally` block's cleanup call is still gated on `shouldDelete` and never fires for the manual path), so a manual-pending file stays visible in the panel indefinitely until either deleted or the entry is otherwise cleaned up — including across `beginRun()`/`hideDeleteNowButton()` for a new upload, which only hides *this tab's* single delete-button widget, not the panel record. `renderPendingDeletions` labels manual entries with a `(수동 삭제 필요)` suffix so they're distinguishable from auto-delete-pending ones in the list.

**Manual entries are deliberately excluded from the disk-space auto-throttle count.** `background.js`'s `vodPipeline:deletionPendingChanged` handler now stores a `manual: boolean` field per pending-deletion record, but `PENDING_DELETION_PAUSE_THRESHOLD`/`PENDING_DELETION_RESUME_THRESHOLD` are compared against `list.filter((d) => !d.manual).length`, not the raw list length — manual-pending files still show up in the panel (`notifyPendingDeletionsToTab` still pushes the full list), they just don't count toward auto-pausing the VOD pipeline. This is intentional: the throttle exists to protect disk space when Studio's confirmation is the only thing standing between "uploaded" and "deleted," a gap that resolves on its own; a manual-pending file depends on the user physically clicking a button, which could take arbitrarily long (or never happen), so including it in the threshold could stall the pipeline indefinitely waiting on human action rather than momentary backlog.

**Banner re-attachment on every state-changing call — a real bug where the console confirmed everything but nothing was visible.** A user reported seeing `[실행 #N] 업로드 확인됨(삭제 설정 꺼짐)` log correctly, yet no manual-delete button ever appeared anywhere on the page, even via `querySelector` from the console (found the element, but `hidden`). The suspected cause: the banner's host element (`BANNER_HOST_ID`, a `position: fixed` div appended once to `document.documentElement`) got detached from the live document at some point during the run — root cause unconfirmed (Studio's SPA doing a broader DOM replacement is the leading theory), but the fix doesn't need the root cause: `showBanner()` used to guard only with `if (document.getElementById(BANNER_HOST_ID)) return;`, and was only ever *called* from `init()` and `restartInThisTab()` — neither of which necessarily runs again during the long (up to 6h) `watchUploadAndDelete` watch, so if the host vanished mid-watch nothing would ever notice or recreate it, and every cached child reference (`bannerMessageEl`, `deleteNowButtonEl`, etc.) would silently keep pointing at now-invisible detached nodes. Fixed two ways: (1) the guard now checks a live reference's `bannerHostEl.isConnected` rather than re-querying by id (catches detachment precisely, not just "was never created"), and (2) `showBanner()` is now called defensively at the top of every function that touches a cached banner element — `setBannerMessage`, `offerManualDelete`, `renderPendingDeletions`, `refreshFolderButton` — so any of these being invoked (which happens continuously throughout a run, including from the long-lived `watchUploadAndDelete`/`onDeleteNowButtonClick` paths) self-heals a detached banner before touching it. `showBanner()` itself removes any orphaned same-id element first (`document.getElementById(BANNER_HOST_ID)?.remove()`) before creating a fresh host + shadow root, which re-binds all the cached element vars from scratch.

**Per-row manual-delete buttons in Studio's video list, addressing the single-banner-button's one-file-at-a-time limit.** The original banner delete button (`deleteNowButtonEl`) can only ever point at one file — whichever was most recently confirmed — so once a second file gets confirmed while the first is still undeleted, there was no way to go back and delete the first one except finding it manually outside the extension. `syncRowDeleteButtons()` (called from `renderPendingDeletions`, i.e. every time the pending-deletions list changes) instead renders one small 🗑 button per **`manual: true`** entry in `latestPendingDeletions`, next to its matching row in Studio's own video list (found via the existing `findRowByTitle`). Deliberately **not** appended as a light-DOM child of `ytcp-video-row` itself — that component is presumed to be a Shadow DOM custom element (unconfirmed against live Studio markup, consistent with the rest of this file's unverified-selector caveats), and a light-DOM child with no matching `<slot>` would silently fail to render at all. Instead, each button lives in its own separate top-level shadow-DOM overlay host (`ROW_BUTTON_HOST_ID`, same `position:fixed` pattern as the banner, one z-index below it) and is positioned purely via `row.getBoundingClientRect()` — this guarantees visibility regardless of Studio's internal rendering, at the cost of needing to re-sync positions periodically (`ROW_BUTTON_SYNC_INTERVAL_MS`, 1.5s, via `startRowButtonsSync`/`stopRowButtonsSync` — the timer only runs while at least one manual-pending entry exists, auto-stopping when the list empties) since Studio's list can scroll/virtualize rows out from under a fixed-position overlay. `syncRowDeleteButtons()` never deletes a row's button just because the row isn't currently found (`display: none` instead) — a row can legitimately scroll out of view and back — only removing it once its underlying pending-deletion entry itself is gone from the list (deleted, or otherwise cleared). Clicking a row button (`onRowDeleteButtonClick`) sends the same `download:deleteUploaded` request as the banner button and the same `notifyPendingDeletion(..., false, true)` cleanup, independently of the banner's own `onDeleteNowButtonClick` (kept as two separate, non-shared implementations rather than factored into one, since the row button's constrained circular shape only has room for a one-character status glyph, not the banner button's full-sentence states). Like the banner, this feature's Shadow DOM/overlay approach has not been exercised against the live Studio page yet.

**This watcher deliberately survives tab reuse.** It captures `videoId`/`fileOrder`/`title` by value at the moment it starts, and — unlike every other per-run helper in this file (`tryAttach`, `autoSaveAndClose`, the `startWatching` poll loop) — never checks `runId !== currentRunId` to bail out early. A real bug was found and fixed here: it originally did check that, so when `youtubeStudio:restart` reused the tab for a new upload (bumping `currentRunId`) while the *previous* upload's file was still transferring in the background (very possible — Studio lets you finish/save metadata and the dialog can close well before the raw upload finishes, which is exactly what makes the tab "reusable" in the first place), the old watcher silently gave up and that file's deletion was never even attempted, with no error surfaced anywhere. Now it runs to completion regardless of how many further reuses happen in the same tab; the only thing gated on `runId === currentRunId` is whether it's still safe/relevant to overwrite the on-screen banner with its result (a stale run's outcome is still logged to console either way, just not shown, so it doesn't clobber a newer run's messages). Multiple such watchers can be in flight concurrently after several reuses — safe, since each only ever reads/writes its own captured `videoId`/`fileOrder`/`title`/DOM row reference, never shared mutable state.

Completion detection went through two rejected approaches before landing on the current one — kept here so they aren't tried again: (1) scanning the upload dialog's text for a percentage/"Uploaded" phrase, abandoned because the exact DOM/wording was never confirmed; (2) dispatching a synthetic `beforeunload` event and reading whether Studio's handler warns, abandoned after live testing showed it reports "warning active" identically whether the upload is in progress or long finished (cause unconfirmed — possibly `event.isTrusted` gating, possibly the dirty-check tracking something unrelated — but empirically useless either way).

The current method (`watchUploadAndDelete` → `waitForLocalUploadDone`) is based on real inspected markup from Studio's video list (the "콘텐츠"/content page, which stays mounted in the DOM underneath the upload dialog overlay while it's open): each `ytcp-video-row` has a `#video-title` anchor with an exact-text `aria-label`, and a `.cell-description` element inside the same row shows the literal text "업로드됨" (confirmed against real markup: `<div class="cell-description ... ytcp-video-row">업로드됨</div>`) once the local file transfer has actually finished — well before the video is publicly live, so it's safe to delete the local copy once seen (whatever HD transcoding/review Studio does afterward doesn't need the local file). `isUploadMarkedDone(row)` compares with **exact equality** after `normalize`, never `.includes()`. This replaced an earlier method that watched the "공개 상태" (visibility) column (`.tablecell-visibility`) for the configured visibility label (e.g. "일부 공개") instead — switched because "업로드됨" is a more direct, setting-independent signal of "the local transfer finished" (the visibility label technically confirms the *publish* step, one layer removed from what this check actually needs to know), and it means `waitForLocalUploadDone`/`watchUploadAndDelete` no longer need a `visibilityLabel` parameter at all.

Row identification (`findRowByTitle(title)`) went through a revision worth remembering: it originally also required the row to currently show a `<ytcp-video-upload-progress uploading>` badge (a cancel-upload control + live percentage), on the theory that only the actively-uploading row could carry that badge, so it doubled as protection against matching a same-titled row from a past, already-finished upload. This broke in practice — confirmed live — because a fast upload can finish (and the badge disappear) between two `UPLOAD_ROW_POLL_MS` (2s) polls, and once gone the badge never reappears, so the row could never be found again and the console showed `"업로드 중" 배지를 찾지 못함` right up to the `UPLOAD_ROW_APPEAR_TIMEOUT_MS` timeout — silently disabling deletion for any upload fast enough to slip between polls. The fix drops the badge requirement entirely and instead relies on the video list's default sort being newest-first (confirmed via `aria-sort="descending"` on the date column header): `findRowByTitle` just returns the **first** exact title match in DOM order, which — under that sort — is the most recent upload, so an older same-titled row (further down) is still never mistaken for the current one, without any timing dependency. `UPLOAD_PROGRESS_BADGE_SELECTOR`/`isRowStillUploading` were removed along with this.

**Suspected residual risk from that same fix, and its mitigation.** Dropping the badge requirement removed one failure mode but reopened a narrower one: taking the *first* title-exact match is only safe if the new row is reliably the first one — if an old row with the exact same title (an earlier attempt, a duplicate re-upload) is still in the list and *already* shows "업로드됨", `findRowByTitle` + `isUploadMarkedDone` could match that stale row and report "done" almost immediately after the new upload starts, before the real new row has even been created — an observed symptom was local files occasionally being deleted right after an upload began. Root cause unconfirmed (never reproduced on demand), but as a cheap, safe mitigation `watchUploadAndDelete` now gates its *entire* completion check (not just the delete step, since a false-positive would equally mislead the VOD pipeline's `fileConfirmed` signal) behind `waitForOwnSaveThenDelay(runId)`: it waits for *this run's own* save-button click (`watchForSave(dialog, runId)` now records `runSavedAt.set(runId, Date.now())` keyed by the run that owns that specific dialog, not the possibly-already-bumped `currentRunId`, so a lingering old dialog's click is never misattributed to a newer run) and then sleeps out the remainder of `MIN_DELAY_AFTER_SAVE_MS` (1 minute) before `findRowByTitle`/`isUploadMarkedDone` are even queried — giving the real new row time to actually appear/update first. If this run's own save is never detected within `OWN_SAVE_WAIT_TIMEOUT_MS` (10min — automation failed before reaching save), the check is abandoned entirely (logged, no confirm/delete sent), same as any other "couldn't confirm" outcome. `runSavedAt` entries are deleted in a `finally` block at the end of `watchUploadAndDelete` to avoid unbounded growth across a long-lived tab's many reuses.

`waitForLocalUploadDone` first waits (`UPLOAD_ROW_APPEAR_TIMEOUT_MS`, 3min) for a title-matching row to appear at all — since our own title-fill (`fillWithVerify`) runs concurrently and may not have overwritten Studio's filename-derived default title yet, this also naturally waits out that race — then keeps the same row reference (never re-queries by title) and waits (`UPLOAD_ROW_DONE_TIMEOUT_MS`, 6h, `UPLOAD_ROW_POLL_MS` interval) for `isUploadMarkedDone` to go true, then re-checks after `UPLOAD_ROW_DONE_CONFIRM_MS` to rule out a one-tick fluke. Any step that can't confirm (row never found, "업로드됨" never shown by timeout) returns `false` and no deletion happens — never optimistic.

**`isUploadMarkedDone` only trusts a *visible* "업로드됨" element, never bare `textContent`.** Suspected (not confirmed) explanation for reports of files being deleted at the wrong moment: Studio's Polymer components elsewhere in this same app are already known to pre-render markup for states that aren't currently active and toggle them with CSS rather than adding/removing nodes (this exact pattern is why `isVisible`/`findVisible` exist and are used throughout the file for menus, buttons, playlist rows, etc.) — if `.cell-description` works the same way, a `<div class="cell-description">업로드됨</div>` could already sit in the DOM, `display:none`, before the file has actually finished transferring, and a bare `row.querySelector(...).textContent` check would match it immediately. `isUploadMarkedDone` therefore does `row.querySelectorAll(UPLOAD_ROW_DESCRIPTION_SELECTOR)` (plural) and only accepts a candidate that passes `isVisible()` — if the one true `.cell-description` is always visible and singular, this is a no-op; if Studio does pre-render alternates, this closes the gap. This has not been confirmed against a real "premature deletion" repro, so if deletions are still happening at the wrong time after this, the next place to look is whether the *visible* element's text briefly flickers to "업로드됨" and back (a fluke `UPLOAD_ROW_DONE_CONFIRM_MS`, 5s, is meant to catch this, but a longer flicker could slip through) or whether the real markup nests the per-state text one level deeper than `.cell-description` itself (in which case `isVisible(cell)` on the outer wrapper wouldn't reflect an inner hidden span).

**Manual "지금 로컬 파일 삭제" button — offered only when auto-delete is off.** When `watchUploadAndDelete` confirms "업로드됨" but `shouldDelete` (`deleteAfterUpload`) is `false`, it now calls `offerManualDelete(videoId, fileOrder)` (only when `showBannerForThis`, same gate as the banner message) instead of just reporting confirmation — this shows a new red button in the banner (`deleteNowButtonEl`, next to the existing folder button) that, on click, sends the exact same `download:deleteUploaded {videoId, fileOrder}` message the automatic path uses. `offerManualDelete`/`hideDeleteNowButton` are separate from `setBannerMessage`/`bannerMessageEl` since the button's target (`deleteNowTarget`) needs to survive independent of whatever text is currently in `.message` — `beginRun()` calls `hideDeleteNowButton()` so a new run's banner never carries over a stale offer for a different file's delete button. `onDeleteNowButtonClick` guards against double-clicks via `deleteNowButtonEl.disabled` and leaves the button disabled with a "✓ 삭제됨" label on success (a fresh `offerManualDelete` call — i.e. a new confirmed file — is what re-enables it), but re-enables it with an error label on failure so the user can retry immediately.

Only on a stable "no warning" does it send `download:deleteUploaded {videoId, fileOrder}` to background, which looks up `downloadedFiles['{videoId}:{fileOrder}'].downloadId` (recorded at download-completion time specifically so deletion never has to re-match by filename — a name-based re-search for a delete op was judged too risky) and calls `chrome.downloads.removeFile(downloadId)`, then marks that record `deletedAt` (so `findDownloadedFile`/`getStorageOverview` stop treating it as present). Any failure to detect completion, find the record, or removeFile just leaves the local file alone and logs why — this path never deletes optimistically.

**Tab reuse — exactly one Studio tab, ever, plus a queue (background.js).** Earlier this fell back to opening a second tab whenever reuse looked unavailable; that was removed after observing that having multiple Studio tabs open caused the *background* (non-focused) one's automation to intermittently fail mid-flow (fill → save → click the post-save close button) — Chrome throttles a hidden tab's timers/rendering, so a button the automation is polling for can simply not appear in time. The fix is to never have more than one Studio tab: `youtubeStudio:open` no longer tries to start the upload itself — it just pushes `{title, description, fileNames, videoId, fileOrder}` onto a `chrome.storage.session` FIFO (`studioUploadQueue`) and responds `{success:true, queued:true}` immediately (`vodFileInfo.js`'s status line reflects "큐에 추가됨", not "reused"/"new tab" — that distinction is gone), then calls `drainStudioQueue()`.

`drainStudioQueue()` (guarded by an in-memory `studioQueueDraining` flag so concurrent calls no-op) processes the queue head-first, one entry at a time, only ever popping an entry once it's confirmed actually handed off:
- No tracked tab (`getStudioTabId()` is `null`, or `chrome.tabs.get` throws because it was closed — cleared both there and in a `tabs.onRemoved` listener) → this is the **only** place a tab is ever created; the new tab's id becomes the permanent `studioTabId`.
- Tracked tab exists → `youtubeStudio:probe` (`isReusable()`); if not reusable, that's normal ("still busy") — stop for now, don't touch the tab, wait for the next trigger.
- Probe says reusable but `youtubeStudio:restart` still returns `{started:false}` — this is the actual failure mode above (tab looked idle but the automation to open a new upload dialog in it didn't work, most likely because it's backgrounded) — recover by `chrome.tabs.reload(tabId)` (rate-limited by `STUDIO_RELOAD_COOLDOWN_MS`, 3min, so a reload that's blocked by a native "leave site?" confirmation — Studio has unsaved state — doesn't spam a fresh dialog on every retry) and leave the queue untouched; a reload that actually goes through makes the tab re-run its content script's `init()`, which is itself queue-aware (see below) and will pick the same head-of-queue entry back up. A reload that's blocked just sits there — nothing is lost, the entry stays queued — until the user deals with the confirmation (letting the reload proceed fires `init()` as above) or the next trigger fires and retries.

Three things trigger `drainStudioQueue()`, so a queued entry is never stuck waiting on just one of them: (1) every `youtubeStudio:open` call, (2) `youtubeStudio:becameIdle` — a fire-and-forget ping the content script sends from the end of `autoSaveAndClose()` once *its own* upload is fully saved (so a newly-idle tab is retried immediately rather than waiting for the next arrival), and (3) the existing `liveCheck` alarm (unconditional, floor 1 minute, already always running) as a pure safety net in case both of the above are missed — it costs nothing when the queue is empty.

`youtubeStudio:init`'s response gained a `managed` flag: a tab tracked as `studioTabsId` that currently has no entry assigned in `pendingStudioUploads` (right after the controlled reload above, or immediately after being newly created and not yet assigned) answers `{pending:false, managed:true}` — and, notably, if the queue is non-empty at that exact moment, `init` itself pops the head entry and answers `{pending:true, ...}` directly, which is what lets a just-reloaded tab resume a stuck request without any further round-trip. The content script only registers `handleBackgroundMessage` (the probe/restart listener) when the response is `pending` **or** `managed` — a `managed:true, pending:false` tab sets a new `explicitlyIdle` flag that makes `isReusable()` return `true` immediately, since none of the normal heuristics (`dialogEverSeen`, `runPhase`) apply to a page that was just wiped by a reload; `beginRun()` clears the flag the moment a real upload actually starts.

The content script still keeps **resettable run state** instead of one-shot module state: `beginRun(payload)` resets title/description/options/fileNames/videoId/fileOrder/attach flags and bumps `currentRunId`, and late callbacks (`tryAttach`, its reaction timeout, the watch timer, `autoSaveAndClose`) compare their captured runId so a superseded run can't write into the new one — **except** `watchUploadAndDelete`, which deliberately keeps running across a reuse (see the delete-after-upload section above; that was a real bug once fixed). `runPhase` ('waiting' → 'automating' → 'ready' → 'saved', the last set by a capturing click listener on `#done-button`) plus `dialogEverSeen` (or `explicitlyIdle`) decide `isReusable()`: never while automating, never while an upload dialog is open and unsaved, never before a dialog was ever seen (a tab that just opened, unless explicitly marked idle). `restartInThisTab` closes a leftover finished upload/share dialog, then `openUploadDialog()` clicks `button[aria-label="만들기"]` first (the menu must be open) → the "동영상 업로드" item (`#text-item-0`, several elements share that id so a visible one is preferred and `querySelectorAll("#text-item-0")[0]` is the fallback) and waits for `ytcp-uploads-dialog`; this sequence was verified by hand in the Studio console. None of this queue/reload machinery has been run end-to-end in the browser yet.

The Studio selectors (the `*_SELECTORS` / `*_SELECTOR` / `VISIBILITY_*` constants at the top of `youtubeStudio.js` — title/description boxes, not-for-kids radio, playlist trigger/popup/done button, visibility radios and step badge) were written from memory of Studio's DOM and have not been verified against the live page — if auto-fill stops working, inspect the relevant element in the upload dialog (the banner's ✗ line says which step failed) and update those constants. The banner's "제목 복사"/"설명 복사" buttons are the manual fallback.

### 다시보기 목록의 유튜브 업로드 여부 판별 (vodList.js + youtubeVideos.js + youtubeMatch.js)

`www.sooplive.com/station/*/vod*` 목록 페이지의 "유튜브 업로드 여부 확인" 버튼이 `vodUpload:match`를 background에 보낸다. 판별 근거는 로컬 기록이 아니라 **내 채널의 실제 업로드 영상**이다: 영상 **설명의 Soop 링크(`sooplive.com/player/{titleNo}`)**로 어느 다시보기인지, **제목의 `[날짜 (n/max)]`**(파일이 하나면 `[날짜]` → 1/1)로 몇 번째 파일인지 맞춘다(`youtubeMatch.js`, 순수 함수). n은 `files` 배열 순서(1부터)이지 `file_order`가 아니다. 영상 목록은 `studio.youtube.com` 탭의 content script(`youtubeVideos.js`)가 Studio 내부 API `creator/list_creator_videos`를 SAPISIDHASH로 호출해 가져오며(열린 Studio 탭이 없으면 background가 잠깐 열었다 닫는다), 이 API의 요청/응답 형식은 기억에 의존해 쓴 것이라 **브라우저에서 검증되지 않았다** — 실패 시 에러에 응답 본문 일부가 담긴다. 결과는 콘솔과 `private-extension:vod-match` window 이벤트(`{pending, uploaded, all}`)로도 나가며, 아래 파이프라인이 이어받는다.

### 다시보기 파이프라인 — 목록 페이지 → 플레이어 페이지 → Studio 탭을 잇는 자동화 (background.js + vodList.js + vodFileInfo.js + youtubeStudio.js)

목록 페이지의 "모두 업로드" 버튼이 시작하는, 여러 다시보기를 무인으로 순서대로 처리하는 파이프라인. 위 "업로드 여부 판별" 기능과는 별개 트리거지만 내부적으로 그 결과(미업로드 목록)를 큐의 시드로 재사용한다(완료된 다시보기를 다시 올리지 않기 위함). background.js가 상태 머신(`chrome.storage.session`의 `vodPipeline: {running, queue, current, done, failed}`)을 들고 있고, 세 종류의 content script가 메시지로만 이어받아 움직인다 — 서로 직접 통신하지 않는다.

**흐름.** (1) `vodList.js`가 `checkMatch()`로 미업로드 다시보기 id를 추린 뒤 `vodPipeline:start {videoIds}`를 보낸다. (2) `advanceVodPipeline()`이 큐 맨 앞을 꺼내 `current`로 놓고, 플레이어 탭을 그 다시보기로 옮긴다(Studio 탭과 같은 이유로 `ensurePipelineTab`이 탭을 하나만 두고 계속 재사용 — `pipelineTabId`; 없으면 그때만 새로 연다). (3) 그 탭에서 `vodFileInfo.js`가 로드되며 `vodPipeline:initPlayer {videoId}`로 "내 차례냐"고 물어 `{active:true}`를 받으면, 패널을 펼치고(`panelElement.classList.remove('collapsed')`) `startPipelineVideoPause()`로 영상 재생을 막은 뒤, `vodPipeline:filesTotal {videoId, fileOrders}`로 완료 판정 기준(그 다시보기의 전체 fileOrder 목록)을 알리고, 버튼 클릭 없이 `renderFiles`가 돌려준 `runBatch()`(기존 "모두 다운로드&업로드"와 완전히 같은 함수)를 스스로 실행한다. 배치가 끝나면(성공/실패 무관) `stopPipelineVideoPause()`로 재생 감시를 풀어준 뒤, 로컬 단계에서 이미 실패했거나(다운로드 실패 등) 손도 못 댄 파일들의 fileOrder를 `vodPipeline:localBatchDone {videoId, failedFileOrders}`로 알린다 — 이 파일들은 Studio 확인 신호가 절대 오지 않을 것이므로 미리 "확인됨"으로 쳐줘야 파이프라인이 무한히 기다리지 않는다. (4) 업로드가 실제로 Studio에 올라간 파일은, 그 Studio 탭의 `watchUploadAndDelete`가 "공개 상태" 라벨 확인을 마치는 시점에 `vodPipeline:fileConfirmed {videoId, fileOrder}`를 보낸다. (5) `fileOrders` 전체가 `confirmedFileOrders ∪ failedFileOrders`로 덮이면(`isCurrentVodSettled`) 그 다시보기를 `done`으로 옮기고 큐의 다음 항목으로 진행 — 탭은 새로 열지 않고 URL만 바꾼다.

**실패가 없었다면 Studio 확인을 기다리지 않고 지름길로 다음 다시보기로 넘어간다(`canFastForwardVod`).** `isCurrentVodSettled`는 Studio가 각 파일의 공개 상태 전환을 실제로 확인해줄 때까지 기다리는데, 다시보기당 파일이 많으면 이 확인 대기가 누적돼 전체 배치가 느려진다. 그래서 `state.hasFailures`(이 파이프라인 실행 전체에서 지금까지 실패가 하나라도 있었는지 — `vodPipeline:start`에서 `false`로 시작해, 파일 로컬 실패(`vodPipeline:localBatchDone`의 `failures`), 다시보기 시간 초과, 플레이어 탭이 닫힘 등 `recordPipelineFailure`가 불리는 모든 지점에서 같이 `true`로 켜진다)가 아직 `false`인 동안은, `current.localBatchDone`(다운로드부터 마지막 파일의 Studio 업로드 요청까지 로컬 단계가 다 끝났다는 뜻 — `vodPipeline:localBatchDone` 수신 시 켜짐)만 켜져도 곧바로 다음 다시보기로 넘어간다(`advanceVodPipeline`의 메인 루프가 `isCurrentVodSettled(current) || canFastForwardVod(state)`를 본다). 지금까지 순조로웠으니 Studio 큐가 나머지 확인을 알아서 끝내줄 거라고 믿고 속도를 내는 것이다. 실패가 하나라도 나온 뒤에는(그 다시보기 자신의 로컬 실패든, 그 전 다시보기의 실패든) 이 지름길을 더 이상 쓰지 않고 원래대로 `isCurrentVodSettled`(전부 확인 또는 시간 초과)까지 기다린다 — 뭔가 잘못되고 있다는 신호가 나온 뒤에는 더 신중하게 가는 것이 안전하다는 판단. 지름길로 넘어간 다시보기에 대해 그 뒤에 뒤늦게 도착하는 `vodPipeline:fileConfirmed`는 그때 `state.current.videoId`가 이미 다음 다시보기로 바뀌어 있어 조용히 무시된다 — 무해하다: 그 확인 신호는 원래도 파이프라인의 진행 여부만 좌우했을 뿐, 로컬 삭제(`watchUploadAndDelete`)는 이 신호와 무관하게 Studio 탭 쪽에서 독립적으로 계속 처리된다.

**배치가 도는 동안은 영상을 재생하지 않는다.** 무인으로 여러 다시보기를 처리하는 동안 실제로 영상이 재생될 필요가 없고(볼 사람이 없음), 재생 자체가 대역폭/리소스만 소모한다. `startPipelineVideoPause()`는 `liveMonitor.js`의 `muteVideo` 접근과 같은 방식으로 `<video>` 엘리먼트를 찾아(플레이어가 페이지 로드 뒤 늦게 만들 수 있어 `MutationObserver`로 계속 지켜봄) 발견 즉시 `pause()`하고, 그 뒤로도 `play` 이벤트를 계속 감시해 무언가(자동재생 재시도 등) 다시 재생을 걸면 즉시 다시 멈춘다. `stopPipelineVideoPause()`가 감시(observer + `play` 리스너)를 해제하기 전까지는 계속 이렇게 동작한다 — 다만 파이프라인이 다음 다시보기로 넘어갈 때는 대부분 `chrome.tabs.update`로 URL 자체를 바꾸기 때문에 content script가 통째로 다시 로드되며 이 상태도 자연히 초기화된다.

**"업로드 확인 감시"는 삭제 설정과 분리했다.** `watchUploadAndDelete`는 원래 "업로드 확인 후 로컬 파일 자동 삭제" 기능 전용이라 `deleteAfterUpload`가 꺼져 있으면 아예 실행되지 않았는데, 파이프라인은 삭제 여부와 무관하게 "이 파일 업로드가 끝났다"는 신호가 꼭 필요하다. 그래서 `DEFAULT_OPTIONS.pipeline` 플래그를 추가해 `tryAttach()`의 감시 시작 조건을 `deleteAfterUpload || pipeline`으로 넓혔고, `watchUploadAndDelete(runId, title, shouldDelete)`는 확인되면 **항상** `vodPipeline:fileConfirmed`를 먼저 보낸 뒤 `shouldDelete`일 때만 삭제를 시도한다(둘 다 꺼져 있으면 애초에 이 함수 자체가 호출 안 됨). `pipeline` 플래그는 `vodFileInfo.js`의 모듈 전역 `pipelineUploadActive`(`maybeRunPipeline`이 `runBatch()`를 감싸는 동안만 true) → `uploadFile()`의 `youtubeStudio:open` 메시지 → background의 Studio 큐 entry → `buildStudioPayload`의 `options.pipeline`까지 그대로 실려간다. 일반 업로드 버튼 클릭(파이프라인이 아닌 경우)은 이 플래그가 항상 false라 기존 동작에 영향이 없다.

**"모두 다운로드&업로드"가 파이프라인에 넘기는 것.** `runDownloadUploadAll`은 이제 `{successOrders, failOrders, cancelled}`를 반환한다. 사람이 보는 배치 요약 문구(`batchStatus`)는 예전 그대로 "실패"와 "처리하지 않은 파일"을 구분해서 보여주지만(취소로 중간에 멈춘 파일은 "실패"로 세지 않는 게 원래 디자인), 반환값의 `failOrders`(파이프라인이 실제로 쓰는 값)는 진짜 실패 + 중단 시점에 다운로드 중이던 파일 + 아예 손 못 댄 파일을 전부 합친 것이다 — 파이프라인 입장에서는 셋 다 "이 fileOrder는 Studio 확인이 절대 안 온다"는 점에서 동일하기 때문. 이 둘을 분리해두지 않으면(처음에 한 번 실수로 합쳤었다) 화면에 실패 개수가 부풀려 보인다.

**탭 이동 순서에 주의.** `advanceVodPipeline`은 `ensurePipelineTab`으로 실제 탭을 옮기기 **전에** `state.current = {videoId, tabId: null, ...}`를 먼저 저장한다 — 순서를 반대로 하면(탭부터 옮기고 나중에 state 저장) 새로 로드된 페이지의 content script가 탭 이동 완료 직후 곧바로 `vodPipeline:initPlayer`를 물었을 때 아직 `state.current`가 안 써져 있어 자기 차례를 놓치는 경합이 실제로 있었다(발견 후 수정). `vodPipeline:initPlayer` 핸들러는 `tabId == null`도 "아직 배정 전이니 이 요청을 보낸 탭을 배정"으로 받아들이도록 이미 관대하게 짜여 있다.

**안전망과 정리.** 어느 신호가 유실돼도(버그, 네트워크 등) `VOD_PIPELINE_TIMEOUT_MS`(12시간)를 넘기면 그 다시보기를 `failed`로 두고 다음으로 넘어간다 — 기존 `liveCheck` 알람(항상 도는 1분 이상 주기)에 `advanceVodPipeline()`을 얹어 이 시간 초과 판정과, 신호가 놓쳤을 때의 재시도를 담당한다. 플레이어 탭이 사용자에 의해 직접 닫히면 `chrome.tabs.onRemoved`가 그 다시보기를 실패로 기록하고 다음으로 진행한다(탭 기록도 지워 다음엔 새로 연다). `vodPipeline:stop`은 `running`을 끄고 현재 탭에 `vodPipeline:cancelCurrent`를 보내 그 자리에서 돌고 있는 배치도 즉시 멈춘다(이미 시작된 Studio 업로드는 그대로 둔다 — "모두 다운로드&업로드"의 중단과 동일한 정책). `vodList.js`는 `vodPipeline:status`를 3초 간격으로 폴링해 진행 상황(`현재 다시보기, 남은 큐, 완료/실패 수`)을 보여주고, 페이지를 새로고침해도 이미 돌고 있는 파이프라인의 진행 상황을 이어서 보여준다.

**일시정지/재개 — 중단과 달리 상태를 보존한 채로 진행만 멈춘다.** `state.paused`(사용자 일시정지)와 `state.throttled`(아래 문단의 자동 스로틀), 그리고 공용 `state.pausedAt`이 추가됐다. 실제로 "멈춰 있다"는 `paused || throttled`이며, 이 OR 결합과 `pausedAt`의 정확한 타이밍(한쪽이 이미 걸려 있으면 다른 쪽이 또 걸려도 `pausedAt`을 덮어쓰지 않고, 둘 다 꺼져야만 그 구간만큼 `current.startedAt`을 밀어주고 정리하는 것)은 공용 헬퍼 `setPipelinePauseFlag(flagName, value)` 하나가 전담한다 — `vodPipeline:pause`/`vodPipeline:resume` 메시지 핸들러는 각각 `setPipelinePauseFlag('paused', true/false)`를 호출하고 그 결과를 그대로 `sendResponse`에 전달할 뿐이다(스로틀 쪽은 `setPipelinePauseFlag('throttled', ...)`를 호출). 이렇게 하지 않으면 오래 멈춰뒀다가 풀리는 순간 `VOD_PIPELINE_TIMEOUT_MS` 시계가 이미 다 돌아버려 시간 초과로 오판할 수 있다(사용자가 멈춰둔 것을 "응답 없음"으로 착각하면 안 되므로). `advanceVodPipeline()`은 루프 맨 앞에서 `state.paused || state.throttled`를 확인해 즉시 `return`한다 — 이미 settled/`canFastForwardVod`로 다음으로 넘어갈 수 있는 상태여도, 심지어 `VOD_PIPELINE_TIMEOUT_MS`를 넘겼어도 멈춰 있는 동안은 그 어떤 판정도 하지 않는다. 현재 다시보기를 처리 중인 플레이어 탭(`vodFileInfo.js`)에도 이 OR 결합 결과(둘 중 하나라도 켜져 있으면 `paused:true`)가 `vodPipeline:setPaused`로 전달돼, `runDownloadUploadAll`이 다음 **파일**을 시작하기 전에 `waitWhilePaused()`로 멈춰 선다 — 이미 시작된 다운로드/업로드는 절대 되돌리지 않고 끝까지 진행한 뒤 파일과 파일 "사이"에서만 대기한다(`shouldCancel()`이 우선이라 멈춰 있는 중에도 "배치 중단"은 즉시 먹힌다). 완전히 재개되는 순간(두 플래그가 모두 꺼졌을 때) `advanceVodPipeline()`을 즉시 호출해, 멈춰 있는 동안 이미 settled/fast-forward 조건을 만족해뒀던 다시보기가 있다면 곧바로 이어서 진행한다. 새로고침 등으로 탭이 다시 로드될 때를 대비해 `vodPipeline:initPlayer` 응답에도 (합쳐진) `paused`를 실어 보내고, `maybeRunPipeline`이 배치를 시작하기 전에 `pipelinePaused`를 그 값으로 미리 맞춰둔다. `vodList.js`의 "일시정지"/"재개" 버튼은 상태를 낙관적으로 바꾸지 않고 다음 `vodPipeline:status` 폴링(최대 3초)에서 실제 `state.paused` 값을 반영한다 — 요청이 실패해도 화면이 실제 상태와 어긋나지 않도록(이 버튼은 `state.throttled`는 건드리지 않는다 — 사용자가 끌 수 있는 건 자기가 건 일시정지뿐이다).

**삭제 대기 파일이 너무 쌓이면 배치를 자동으로 스로틀한다(디스크 공간 안전장치).** `canFastForwardVod`의 지름길 덕분에 파이프라인이 Studio의 업로드 확인 속도보다 훨씬 빠르게 다음 다시보기로 넘어갈 수 있게 됐는데, 그러면 "로컬에서 지워도 되는지 아직 확인 안 된" 파일이 디스크에 계속 쌓일 위험이 있다. 그래서 `youtubeStudio.js`의 `watchUploadAndDelete`는 삭제 대상 파일을 감시하기 시작/끝낼 때마다 `notifyPendingDeletion(videoId, fileOrder, title, pending, manual)` → `vodPipeline:deletionPendingChanged` 메시지로 background에 알린다. background는 `pendingDeletions`(`chrome.storage.session`, `{key, videoId, fileOrder, title, manual, startedAt}` 배열)로 이 목록을 유지하다가, **자동 삭제 대상(`manual:false`) 개수만**(수동 삭제 대상은 제외 — 아래 참고) `PENDING_DELETION_PAUSE_THRESHOLD`(10) 이상이 되면 `setPipelinePauseFlag('throttled', true)`로 자동 일시정지하고, `PENDING_DELETION_RESUME_THRESHOLD`(9) 이하로 내려오면 자동 재개한다 — 정지/재개 문턱을 하나로 하지 않고 10/9로 가른 것은 개수가 문턱 근처에서 오르내릴 때 일시정지·재개가 잦게 토글되는 것을 막기 위함이다. 이 목록은 파이프라인 실행 여부와 무관하게(수동 업로드에서도) 계속 추적되며, 스로틀 판단은 `state.running`일 때만 적용된다. `vodPipeline:getPendingDeletions`는 이 목록을 그대로 돌려주고(패널이 처음 뜰 때 초기 상태를 채우는 용도), 목록이 바뀔 때마다 `notifyPendingDeletionsToTab`이 현재 Studio 탭(`getStudioTabId()`)에 `vodPipeline:pendingDeletionsUpdated {deletions}`를 push한다.

**자동 삭제(`deleteAfterUpload`)가 꺼져 있는 수동 삭제 대상(`manual:true`)도 이 목록에 포함된다.** 확인된 시점(`watchUploadAndDelete`가 "업로드됨"을 확인해 수동 삭제 버튼을 띄우는 시점)에 `notifyPendingDeletion(..., true, true)`로 올라가고, 사용자가 실제로 "지금 로컬 파일 삭제" 버튼을 눌러 성공했을 때(`onDeleteNowButtonClick`)만 `pending:false`로 내려간다 — 즉 확인 후 지워질 때까지 계속 목록/패널에 남아 있다. 단 자동 스로틀 문턱 계산에는 넣지 않는다 — 사용자가 버튼을 언제 누를지(또는 영영 안 누를지) 알 수 없는데 그걸로 파이프라인이 무한정 멈추면 안 되기 때문. (예전엔 `tryAttach()`가 `deleteAfterUpload`도 `pipeline`도 꺼져 있으면 `watchUploadAndDelete` 자체를 아예 부르지 않는 버그가 있었다 — 일반 수동 업로드에서는 이 감시가 영원히 시작되지 않아 "지금 로컬 파일 삭제" 버튼도, 이 패널의 항목도 절대 생기지 않았다. 지금은 삭제 설정과 무관하게 항상 감시가 시작된다.)

**Studio 배너의 "삭제 대기 중인 파일" 접이식 패널.** `youtubeStudio.js`의 배너(`showBanner()`)에 목록을 추가하면 창이 길어져 화면을 가릴 수 있으므로 기본은 접혀 있다(`pendingDeletionsExpanded`, 토글 버튼으로 펼침/접힘 전환, 펼쳐도 목록 자체는 `max-height`로 스크롤된다). 배너가 새로 만들어질 때(탭 재사용 시에는 한 번만 만들어짐) `vodPipeline:getPendingDeletions`로 현재 목록을 물어 초기 렌더링을 하고, 이후에는 `handleBackgroundMessage`가 받는 `vodPipeline:pendingDeletionsUpdated` push로 `renderPendingDeletions()`가 다시 그린다. 목록 항목은 `textContent`로만 채워 넣는다(제목에 특수문자가 있어도 `innerHTML` 이스케이프를 신경 쓸 필요가 없도록). `manual:true` 항목은 제목 뒤에 `(수동 삭제 필요)`를 붙여 자동 삭제 대상과 구분한다.

**실패는 반드시 사용자에게 알린다(`recordPipelineFailure`, background.js).** 무인으로 여러 다시보기를 처리하다 보면 아무도 안 보고 있을 때 실패가 나올 수 있으므로, 파일 하나 또는 다시보기 하나가 실패하는 모든 지점(로컬 다운로드/업로드 요청 실패 — `vodPipeline:localBatchDone`의 `failures`, 다시보기 시간 초과, 플레이어 탭이 닫힘)에서 이 함수를 거친다. 세 가지를 한 번에 한다: (1) `console.warn`으로 로그를 남기고, (2) `chrome.storage.local`의 `pipelineFailureHistory` 배열에 `{at, type: 'vod'|'file', videoId, fileOrder?, reason}`를 추가해 영구 기록한다 — `vodPipeline` 자체는 `storage.session`이라 브라우저를 닫으면 사라지지만 이 히스토리는 남는다(최대 `PIPELINE_FAILURE_HISTORY_MAX`=200개, 넘으면 오래된 것부터 버림). (3) `chrome.notifications.create`로 데스크톱 알림을 띄운다 — 아이콘은 별도 이미지 파일 대신 32x32 빨간 원을 그려 넣은 데이터 URL(`PIPELINE_FAILURE_ICON_DATA_URL`)을 인라인했다(`notifications` 권한이 manifest에 추가됨). 알림 생성이 실패해도(권한 문제 등) 히스토리 기록은 이미 끝난 뒤라 영향받지 않는다. `runDownloadUploadAll`의 반환값도 `failOrders: [{fileOrder, reason}]`로(예전엔 fileOrder 숫자만) 바뀌어 각 실패의 구체적인 이유(다운로드 실패 사유, 업로드 시작 실패 사유, 중단으로 인한 미처리 등)가 그대로 여기까지 실려온다. 시간 초과로 다시보기를 포기할 때는 그 시점에 아직 확인 안 된 fileOrder들을 이유 문자열에 나열해준다(`시간 초과 (확인 안 된 파일: 1, 2)`).

이 다시보기 파이프라인 전체(탭 간 메시지 흐름, 타이밍, 데스크톱 알림이 실제로 뜨는지)는 아직 실제 브라우저에서 처음부터 끝까지 돌려보지 않았다 — 상태 머신과 실패 기록 로직 자체는 가짜 chrome API로 여러 시나리오를 테스트했지만, 실제 Soop/Studio 페이지에서의 타이밍(페이지 로드 속도, Studio 큐와 파이프라인 큐가 동시에 도는 상황 등)과 실제 `chrome.notifications` 동작은 검증되지 않았다.

### Legacy/unused files

`src/popup.html`, `popup.js`, `styles.css`, `soopHandler.js`, `taskRunner.js`, `dummy.js` are **not referenced by `manifest.json`** — superseded by the in-page panel (`content.js`) and the options page. Don't extend them and don't assume they run; they're kept around but dead.

## Conventions

- UI copy, comments, and commit messages are in Korean; match that when editing existing files.
- Logging in the live-monitor subsystem is tagged `[LiveMonitor]` in both `background.js` and `liveMonitor.js` — keep using that tag for related additions so logs stay filterable.
- In `youtubeStudio.js`, every log line tied to a specific upload run is tagged `[YoutubeStudio] [실행 #N]` via the `runTag(runId)` helper (`N` is that run's `currentRunId` at the moment `beginRun()` started it — a monotonic per-tab counter, not tied to any particular file otherwise) rather than the bare `LOG_TAG`. This exists because the tab is reused across many uploads (see "Tab reuse" above) and several runs' async work can genuinely overlap (`watchUploadAndDelete` deliberately outlives its own run) or interleave in the console, so a log line with no run number is ambiguous about which upload it's about. Call sites that already have a captured `runId` in scope (`runAutomation`, `autoSaveAndClose`, `watchForSave`, `watchUploadAndDelete`, `safely`, the `startWatching` poll closure) must pass it explicitly — using `currentRunId` there instead would mislabel a lagging old run's log line with whatever new run has since started (exactly the ambiguity this exists to prevent). Call sites with no run context of their own (`beginRun`, `restartInThisTab`, `openUploadDialog`, `setupFolderAccess`, `onFolderButtonClick`) call `runTag()` with no argument, which defaults to the current `currentRunId` — correct for them since they always execute during, or synchronously kick off, the run they're logging about. The one `console.log` with no run tag at all is the version-load line at the top of the file, since it fires before any run has ever started. `currentRunId` is incremented in exactly one place, `beginRun()` — a real bug (found via this same run-tagging, when a user noticed the number seemed to jump by more than 1 per file) had `restartInThisTab` also incrementing it itself right before calling `beginRun()` (which increments it again), so every tab reuse skipped a run number (1 → 3 → 5 → ...) instead of counting files 1:1. Fixed by removing the increment from `restartInThisTab` and leaving it solely to `beginRun()`.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"나만의 SOOP 확프" — a Manifest V3 Chrome extension for Soop (sooplive.com, formerly AfreecaTV). No bundler, no framework, no package.json: every file in `src/` is a plain script loaded directly by `manifest.json`. There is no build step.

## Commands

There is no build/lint/test tooling in this repo. Development loop:

- **Syntax-check a file after editing it**: `node --check src/<file>.js` (works for both classic scripts and the ES-module `background.js`/`soopLiveApi.js` on modern Node).
- **Validate manifest.json**: `node -e "JSON.parse(require('fs').readFileSync('manifest.json','utf8'))"`.
- **Manual test**: load unpacked at `chrome://extensions` (enable Developer mode → "압축해제된 확장 프로그램을 로드합니다" → select the repo root), then reload the extension after each change.
- **Background logs**: `chrome://extensions` → this extension's "service worker" link opens its DevTools console.
- **Content script logs** (panel, live monitor, etc.): open DevTools on the relevant `play.sooplive.com` tab.

## Architecture

### No bundler ⇒ shared JS world per content_scripts entry

Content scripts listed together in one `content_scripts` entry of `manifest.json` execute in the same isolated-world JS context on that page, so top-level `const`/`function` names in one file are visible to the others in the same entry and can collide. `content.js` and `songSearch.js` rely on this (deliberately share globals like `SongSearch`). Scripts that don't need to share state (`disableAutoPlay.js`, `hideBroadcastButton.js`, `liveMonitor.js`) are wrapped in an IIFE — keep doing this for new standalone content scripts.

`background.js` is the only ES module (`"type": "module"` in manifest) and is the only place that can `import` from `soopLiveApi.js`.

### Settings: one storage key, feature-gated

All configuration lives under a single `chrome.storage.local` key, `settings`, shaped as `{ features: { <featureName>: {...} } }`. Each feature object has at minimum `enabled: boolean`. This schema is intentionally duplicated (not shared via an imported module) as `DEFAULT_SETTINGS` in both `src/background.js` and `src/options.js` — when adding a new feature, update both, plus the corresponding UI block in `src/options.html`/`src/options.js` (a `.switch` toggle + optional fields, following the existing card markup).

Classic content scripts that gate a simple on/off feature (`disableAutoPlay.js`, `hideBroadcastButton.js`, and the panel init in `content.js`) do a lightweight one-off check instead of importing the full defaults:

```js
chrome.storage.local.get(['settings']).then(({ settings }) => {
  if (settings?.features?.<name>?.enabled === false) return; // default-on: undefined means enabled
  // ... run the feature
});
```

Follow this pattern for any new simple content-script toggle rather than pulling in `DEFAULT_SETTINGS`.

The extension icon has no `default_popup` (see `manifest.json`'s empty `action`), so `chrome.action.onClicked` in `background.js` opens the options page (`options_ui` in manifest, `open_in_tab: true`) instead.

### Live-monitor feature (background.js + soopLiveApi.js + liveMonitor.js)

This is the most involved subsystem. Key design points, in case they need to be extended:

- **All Soop API calls happen in `background.js`** (via `soopLiveApi.js`'s `isStreamerLive`/`getChannelBroad`, hitting `api-channel.sooplive.com`), never from content scripts — background/extension contexts get CORS-free fetches for `host_permissions` origins; content scripts don't (their fetch/XHR is bound by the *page's* origin for CORS, regardless of host_permissions). `soopLiveApi.js` is a minimal in-repo port of `GetChannelBroad` from the sibling project `../VOD-Master/src/.test/soop_api_standalone.js`; if more Soop API surface is needed later, that file is the source to port from (not a runtime dependency).
- **`chrome.alarms` (`liveCheck`, min. 1 minute — a Chrome-enforced floor)** drives periodic polling of registered streamers. `chrome.storage.session` holds the ephemeral `monitoredTabs: {tabId: streamerId}` map, which scopes "auto-managed" tabs. This is why `liveMonitor.js` always starts by asking background `liveMonitor:init` and does nothing if the answer is `monitored: false` — tabs the user opens manually are never touched.
- **The per-tick decision is level-triggered, not edge-triggered**: on every alarm tick, for each enabled streamer, the rule is simply "is live && has no open monitored tab" → open a tab. This single rule intentionally covers both the first time a stream goes live and recovery when a monitored tab was closed unexpectedly (crash, accidental close) while the stream was still live — no separate "previous state" bookkeeping needed.
- **Tabs are opened with a brief real focus, then handed back.** Soop's player does not appear to start streaming in a tab that's never been the active tab, so `runLiveCheck` creates the tab with `active: true`, remembers the previously-active tab, and `liveMonitor.js` detects true playback start (video `currentTime` advancing) and sends `liveMonitor:playbackStarted` so background can restore focus to the original tab (`FOCUS_RESTORE_FALLBACK_MS` is a safety timeout in case that signal never arrives). The video is muted (`muteVideo` in `liveMonitor.js`) as soon as it's found, precisely because this focus hand-off is real.
- **End-of-broadcast detection is deliberately two-step**, because "video stopped" is ambiguous (real end vs. network hiccup vs. being kicked): `liveMonitor.js` detects a stall/`ended`/`error` on the `<video>`, then asks background to re-check the live API on demand (`liveMonitor:checkStillLive`) rather than trusting the last polled state. Still live → `location.reload()` (capped by `MAX_RELOAD_ATTEMPTS`, counted in `sessionStorage` so the cap survives the reload). Actually offline → shows the countdown overlay and closes the tab (`liveMonitor:closeTab`) unless the user clicks "닫지 않기".

### VOD file listing (vodFileInfo.js)

The panel's file list comes from `getSoopVodInfo` (`station/video/a/view`, `files[]`); the download/upload flow separately calls `chk_download_auth.php`'s `szWork=LIST` (`FILE_LIST[]`) to get download-eligible entries. Both arrays carry a `file_order` field, but **`file_order` is not guaranteed to start at 1 or be contiguous per-VOD** — a VOD can legitimately have `files` numbered e.g. 3, 4, 5 (observed in practice) when earlier segments of the same broadcast belong to a different `title_no`. `buildFileMeta` therefore stores the real `fileOrder: Number(file.file_order)` per panel item, and both the download button and the upload title/attach-name lookup match `FILE_LIST` entries by `f.file_order === meta.fileOrder` — never by `meta.index + 1`. Using the array position instead of the real `file_order` was a real bug (found via VOD title_no 106472213, whose `files` were numbered 3/4/5): it silently failed to find a `FILE_LIST` entry for most items, and could even match the wrong file when an index+1 guess coincidentally hit a real `file_order`.

**"모두 다운로드&업로드" batch.** `runDownloadUploadAll` walks the files strictly one at a time: `downloadFile()` starts the download (returns `downloadId`), then `waitForDownloadOutcome(downloadId)` blocks until the download is confirmed finished, and only then `uploadFile()` runs (opens/reuses a Studio tab via `youtubeStudio:open`) before the loop moves on to the next file's download. `downloadFile`/`uploadFile` are the same functions the per-file buttons use (the buttons are thin wrappers), so both paths stay in sync. Completion is detected through storage, not a held-open message channel: background's `chrome.downloads.onChanged` listener writes `downloadOutcomes[downloadId] = {ok, name | error, recordedAt}` to `chrome.storage.local` (alongside the durable `downloadedFiles` name record), and the content script polls it (`DOWNLOAD_OUTCOME_POLL_MS`, up to `DOWNLOAD_WAIT_TIMEOUT_MS`) and deletes the entry it consumed — a service worker can die during a multi-GB download, but storage survives (same reasoning as `pendingDownloads`). Ordinary manual downloads never consume their outcome, so `pruneOldDownloadOutcomes` drops entries older than 24h on each write. Deliberate simplifications: the loop does **not** wait for the Studio-side automation (fill/save/close) of file *n* to finish before starting file *n+1*'s download — if that tab is still busy when file *n+1*'s upload starts, `tryReuseStudioTab` correctly refuses it and a new tab opens; a failed download is recorded on that file's status line and the batch continues with the next file rather than aborting; the summary counts "upload started", not "upload finished". All per-file buttons and the batch button are disabled while it runs. A red "배치 중단" button (visible only while running) sets a local `cancelled` flag: `waitForDownloadOutcome` takes a `shouldCancel` callback and returns `{cancelled:true}`, the in-flight download is cancelled via a `download:cancel` message (background calls `chrome.downloads.cancel`), the loop stops before starting any further file, and the summary reports how many files were left untouched. Uploads already started (Studio tabs) are not undone.

### YouTube upload helper (vodFileInfo.js + background.js + youtubeStudio.js)

Uploading is done through **YouTube Studio's own uploader**, not the YouTube Data API. An earlier version used `videos.insert` (OAuth via `chrome.identity`, resumable upload streamed from the content script through background) and was removed: in practice it was noticeably slower end-to-end than uploading in Studio directly (both the transfer and the post-upload processing/checks, as observed), and per YouTube's API policy videos uploaded via `videos.insert` from an unverified API project are locked to private until the project passes an audit. Don't reintroduce the API route without weighing that.

Flow: the "유튜브에 업로드" button in `vodFileInfo.js` sends `{action:'youtubeStudio:open', title, description}` to background, which opens `https://www.youtube.com/upload` (redirects into Studio's upload dialog) in a new tab and stores the title/description in `chrome.storage.session` under `pendingStudioUploads[tabId]` (per-tab, so several upload tabs opened back-to-back don't get mixed up; cleaned on `tabs.onRemoved`). `youtubeStudio.js` (content script on `studio.youtube.com`) asks `youtubeStudio:init` and does nothing unless the answer is `pending: true` — same "only touch tabs we opened" gate as `liveMonitor.js`. It then polls for the title/description boxes **inside `ytcp-uploads-dialog` only** (the same boxes exist on the edit page of already-uploaded videos, so unscoped filling could overwrite a real video's title), fills them via `execCommand` (plain value assignment isn't picked up by Studio's Polymer bindings) and re-verifies a few times because Studio also auto-fills the title from the filename after the box appears. The file itself can't be handed over as bytes — `chrome.runtime` messaging is JSON-only (a `File` arrives with `size` undefined and an `ArrayBuffer` as `{}`; base64 strings are the only way to move bytes through it) — and a path string can't fill an `<input type="file">`. The working route is the File System Access API: `youtubeStudio.js` shows a banner button (a folder picker needs a user click) that lets the user grant the download folder once; the `FileSystemDirectoryHandle` is kept in the **Studio page origin's** IndexedDB (a handle can't cross between the extension's own pages and a content script's page). Then `tryAttach()` finds the file by exact name (`buildNameMatchers`: the name, Chrome's ` (n)` duplicate suffix, and Windows-illegal characters replaced by `-` (what `sanitizeFileName` in background and Soop's official download do) or `_` (Chrome's own sanitizing) — never partial matches, since `_1.mp4` vs `_10.mp4` would otherwise collide), builds a `File` from the handle, puts it into the dialog's file input via `DataTransfer` and dispatches `input`/`change`. Failure at any point (no permission, file not found, Studio not reacting) falls back to the user picking the mp4 manually. Chrome blocks the OS-default Downloads folder itself in the picker, hence the `downloadSubfolder` setting (relative to Chrome's download dir; `chrome.downloads` only accepts relative paths) — background applies it in `download:start`, and `findDownloadedFile()` also descends into that subfolder if a parent was connected. To match the file that was *actually* saved (Chrome sanitizes names and appends ` (1)` on duplicates), `download:start` first runs the filename through `sanitizeFileName` (illegal characters → `-`; unsanitized names made `chrome.downloads` fail with an invalid-filename error, while the upload **title** keeps the original unsanitized `file_name`), then records `pendingDownloads[downloadId]` in `chrome.storage.local` (not memory — the service worker can be killed during a long download) and `chrome.downloads.onChanged` writes the final basename to `downloadedFiles['{videoId}:{fileOrder}']` on completion; `vodFileInfo.js` passes that (plus Soop's original `file_name`) as `fileNames` to `youtubeStudio:open`. Beyond file attachment and title/description it also applies the saved options `settings.features.vodFileInfo.{youtubeNotForKids, youtubePlaylists, youtubeVisibility}` (edited in the options page; background passes them in the `youtubeStudio:init` response so defaults stay in one place): click the "not made for kids" radio, open the playlist dropdown, **wait for the account's playlists to actually load** (the popup opens empty and fills asynchronously — `waitForPlaylistRows` waits until rows appear and their count stops changing for `PLAYLIST_STABLE_MS`, and each name then gets a short extra grace `PLAYLIST_ROW_GRACE_MS` for batches that arrive later than that window; ticking immediately made every name "not found"), and tick each configured playlist **by exact name** (multi-select; no partial matching, so a similarly named playlist is never picked silently), then jump to the visibility step and click the configured radio. Each step runs independently via `safely()` — one failing doesn't block the others — and the banner shows ✓/✗ per step.

**Auto-save (toward full automation).** If every step above succeeds (`results.every(r => r.ok)`), `autoSaveAndClose()` clicks the save button (`DONE_BUTTON_SELECTOR`, `#done-button` — confirmed working) itself instead of waiting for the user, then polls (`findSaveCompletionCloseButton`, up to `SAVE_PROCESSING_TIMEOUT_MS`) for the "닫기"/"Close" button that appears afterward and clicks that too. If any earlier step failed, save is never attempted and the dialog is left for the user, same as before. The close button was confirmed by hand as a plain `<button aria-label="닫기">` with no id (`DIALOG_CLOSE_BUTTON_SELECTORS` tries `button[aria-label="닫기"]`/`"Close"` first, then falls back to text match and the older `#close-button` guess) — but **its container isn't scoped** to `UPLOAD_DIALOG_SELECTOR`/`SHARE_DIALOG_SELECTOR` the way every other step's lookup is, because that container tag is itself unconfirmed; `findSaveCompletionCloseButton`/`findVisibleButtonByText` instead search the whole `document` for a *visible* match (`findVisible`/`isVisible`, the same visibility-first approach as the "만들기" button and menu item). This is deliberately looser than the rest of the file's dialog-scoped selectors — acceptable here since it only runs in the few seconds right after our own scripted save click. If auto-save or the close click still doesn't work, check the console for `[YoutubeStudio] 저장 버튼(...)을 찾지 못함` / `완료 화면의 닫기 버튼을 찾지 못함`. `watchForSave`'s click listener on the dialog catches the scripted save click the same way it catches a manual one, so `runPhase` still flips to `'saved'` and tab reuse (`isReusable()`) keeps working unchanged.

**Delete local file after upload confirmed (opt-in, default off).** `settings.features.vodFileInfo.deleteLocalFileAfterUpload` (options page, red-flagged warning text, default `false` since this is destructive) flows through `buildStudioPayload`'s `options.deleteAfterUpload` and `youtubeStudio:open`'s `videoId`/`fileOrder` (added alongside `title`/`description`/`fileNames`; `vodFileInfo.js`'s `uploadFile()` always sends `meta.fileOrder`, the real Soop `file_order`, regardless of whether the Studio-side attach later succeeds). In `youtubeStudio.js`, `watchUploadAndDelete(runId, title)` is only started from inside `tryAttach()`'s success branch — i.e. only when **our own automatic attach** put a specific known local file into the input, never when the user picked a file manually (we'd have no way to know if that matches `videoId`/`fileOrder`).

**This watcher deliberately survives tab reuse.** It captures `videoId`/`fileOrder`/`title` by value at the moment it starts, and — unlike every other per-run helper in this file (`tryAttach`, `autoSaveAndClose`, the `startWatching` poll loop) — never checks `runId !== currentRunId` to bail out early. A real bug was found and fixed here: it originally did check that, so when `youtubeStudio:restart` reused the tab for a new upload (bumping `currentRunId`) while the *previous* upload's file was still transferring in the background (very possible — Studio lets you finish/save metadata and the dialog can close well before the raw upload finishes, which is exactly what makes the tab "reusable" in the first place), the old watcher silently gave up and that file's deletion was never even attempted, with no error surfaced anywhere. Now it runs to completion regardless of how many further reuses happen in the same tab; the only thing gated on `runId === currentRunId` is whether it's still safe/relevant to overwrite the on-screen banner with its result (a stale run's outcome is still logged to console either way, just not shown, so it doesn't clobber a newer run's messages). Multiple such watchers can be in flight concurrently after several reuses — safe, since each only ever reads/writes its own captured `videoId`/`fileOrder`/`title`/DOM row reference, never shared mutable state.

Completion detection went through two rejected approaches before landing on the current one — kept here so they aren't tried again: (1) scanning the upload dialog's text for a percentage/"Uploaded" phrase, abandoned because the exact DOM/wording was never confirmed; (2) dispatching a synthetic `beforeunload` event and reading whether Studio's handler warns, abandoned after live testing showed it reports "warning active" identically whether the upload is in progress or long finished (cause unconfirmed — possibly `event.isTrusted` gating, possibly the dirty-check tracking something unrelated — but empirically useless either way).

The current method (`watchUploadAndDelete` → `waitForLocalUploadDone`) is based on real inspected markup from Studio's video list (the "콘텐츠"/content page, which stays mounted in the DOM underneath the upload dialog overlay while it's open): each `ytcp-video-row` has a `#video-title` anchor with an exact-text `aria-label`, and its "공개 상태" (visibility) column cell (`.tablecell-visibility`, confirmed against real markup down to the exact `normalize(textContent)` result) shows the exact configured-visibility label (`VISIBILITY_LABELS`, e.g. "일부 공개") once upload has gotten far enough along — well before it's actually live, so it's safe to delete the local copy once seen (whatever HD transcoding/review Studio does afterward doesn't need the local file). `isVisibilityShown(row, expectedLabel)` compares with **exact equality** after `normalize` — never `.includes()`, because "공개" is a literal substring of both "비공개" and "일부 공개", so a substring check would confuse all three visibility levels with each other.

Row identification (`findRowByTitle(title)`) went through a revision worth remembering: it originally also required the row to currently show a `<ytcp-video-upload-progress uploading>` badge (a cancel-upload control + live percentage), on the theory that only the actively-uploading row could carry that badge, so it doubled as protection against matching a same-titled row from a past, already-finished upload. This broke in practice — confirmed live — because a fast upload can finish (and the badge disappear) between two `UPLOAD_ROW_POLL_MS` (2s) polls, and once gone the badge never reappears, so the row could never be found again and the console showed `"업로드 중" 배지를 찾지 못함` right up to the `UPLOAD_ROW_APPEAR_TIMEOUT_MS` timeout — silently disabling deletion for any upload fast enough to slip between polls. The fix drops the badge requirement entirely and instead relies on the video list's default sort being newest-first (confirmed via `aria-sort="descending"` on the date column header): `findRowByTitle` just returns the **first** exact title match in DOM order, which — under that sort — is the most recent upload, so an older same-titled row (further down) is still never mistaken for the current one, without any timing dependency. `UPLOAD_PROGRESS_BADGE_SELECTOR`/`isRowStillUploading` were removed along with this.

`waitForLocalUploadDone` first waits (`UPLOAD_ROW_APPEAR_TIMEOUT_MS`, 3min) for a title-matching row to appear at all — since our own title-fill (`fillWithVerify`) runs concurrently and may not have overwritten Studio's filename-derived default title yet, this also naturally waits out that race — then keeps the same row reference (never re-queries by title) and waits (`UPLOAD_ROW_DONE_TIMEOUT_MS`, 6h, `UPLOAD_ROW_POLL_MS` interval) for `isVisibilityShown` to go true, then re-checks after `UPLOAD_ROW_DONE_CONFIRM_MS` to rule out a one-tick fluke. Any step that can't confirm (row never found, label never shown by timeout) returns `false` and no deletion happens — never optimistic.

Only on a stable "no warning" does it send `download:deleteUploaded {videoId, fileOrder}` to background, which looks up `downloadedFiles['{videoId}:{fileOrder}'].downloadId` (recorded at download-completion time specifically so deletion never has to re-match by filename — a name-based re-search for a delete op was judged too risky) and calls `chrome.downloads.removeFile(downloadId)`, then marks that record `deletedAt` (so `findDownloadedFile`/`getStorageOverview` stop treating it as present). Any failure to detect completion, find the record, or removeFile just leaves the local file alone and logs why — this path never deletes optimistically.

**Tab reuse — exactly one Studio tab, ever, plus a queue (background.js).** Earlier this fell back to opening a second tab whenever reuse looked unavailable; that was removed after observing that having multiple Studio tabs open caused the *background* (non-focused) one's automation to intermittently fail mid-flow (fill → save → click the post-save close button) — Chrome throttles a hidden tab's timers/rendering, so a button the automation is polling for can simply not appear in time. The fix is to never have more than one Studio tab: `youtubeStudio:open` no longer tries to start the upload itself — it just pushes `{title, description, fileNames, videoId, fileOrder}` onto a `chrome.storage.session` FIFO (`studioUploadQueue`) and responds `{success:true, queued:true}` immediately (`vodFileInfo.js`'s status line reflects "큐에 추가됨", not "reused"/"new tab" — that distinction is gone), then calls `drainStudioQueue()`.

`drainStudioQueue()` (guarded by an in-memory `studioQueueDraining` flag so concurrent calls no-op) processes the queue head-first, one entry at a time, only ever popping an entry once it's confirmed actually handed off:
- No tracked tab (`getStudioTabId()` is `null`, or `chrome.tabs.get` throws because it was closed — cleared both there and in a `tabs.onRemoved` listener) → this is the **only** place a tab is ever created; the new tab's id becomes the permanent `studioTabId`.
- Tracked tab exists → `youtubeStudio:probe` (`isReusable()`); if not reusable, that's normal ("still busy") — stop for now, don't touch the tab, wait for the next trigger.
- Probe says reusable but `youtubeStudio:restart` still returns `{started:false}` — this is the actual failure mode above (tab looked idle but the automation to open a new upload dialog in it didn't work, most likely because it's backgrounded) — recover by `chrome.tabs.reload(tabId)` (rate-limited by `STUDIO_RELOAD_COOLDOWN_MS`, 3min, so a reload that's blocked by a native "leave site?" confirmation — Studio has unsaved state — doesn't spam a fresh dialog on every retry) and leave the queue untouched; a reload that actually goes through makes the tab re-run its content script's `init()`, which is itself queue-aware (see below) and will pick the same head-of-queue entry back up. A reload that's blocked just sits there — nothing is lost, the entry stays queued — until the user deals with the confirmation (letting the reload proceed fires `init()` as above) or the next trigger fires and retries.

Three things trigger `drainStudioQueue()`, so a queued entry is never stuck waiting on just one of them: (1) every `youtubeStudio:open` call, (2) `youtubeStudio:becameIdle` — a fire-and-forget ping the content script sends from the end of `autoSaveAndClose()` once *its own* upload is fully saved (so a newly-idle tab is retried immediately rather than waiting for the next arrival), and (3) the existing `liveCheck` alarm (unconditional, floor 1 minute, already always running) as a pure safety net in case both of the above are missed — it costs nothing when the queue is empty.

`youtubeStudio:init`'s response gained a `managed` flag: a tab tracked as `studioTabsId` that currently has no entry assigned in `pendingStudioUploads` (right after the controlled reload above, or immediately after being newly created and not yet assigned) answers `{pending:false, managed:true}` — and, notably, if the queue is non-empty at that exact moment, `init` itself pops the head entry and answers `{pending:true, ...}` directly, which is what lets a just-reloaded tab resume a stuck request without any further round-trip. The content script only registers `handleBackgroundMessage` (the probe/restart listener) when the response is `pending` **or** `managed` — a `managed:true, pending:false` tab sets a new `explicitlyIdle` flag that makes `isReusable()` return `true` immediately, since none of the normal heuristics (`dialogEverSeen`, `runPhase`) apply to a page that was just wiped by a reload; `beginRun()` clears the flag the moment a real upload actually starts.

The content script still keeps **resettable run state** instead of one-shot module state: `beginRun(payload)` resets title/description/options/fileNames/videoId/fileOrder/attach flags and bumps `currentRunId`, and late callbacks (`tryAttach`, its reaction timeout, the watch timer, `autoSaveAndClose`) compare their captured runId so a superseded run can't write into the new one — **except** `watchUploadAndDelete`, which deliberately keeps running across a reuse (see the delete-after-upload section above; that was a real bug once fixed). `runPhase` ('waiting' → 'automating' → 'ready' → 'saved', the last set by a capturing click listener on `#done-button`) plus `dialogEverSeen` (or `explicitlyIdle`) decide `isReusable()`: never while automating, never while an upload dialog is open and unsaved, never before a dialog was ever seen (a tab that just opened, unless explicitly marked idle). `restartInThisTab` closes a leftover finished upload/share dialog, then `openUploadDialog()` clicks `button[aria-label="만들기"]` first (the menu must be open) → the "동영상 업로드" item (`#text-item-0`, several elements share that id so a visible one is preferred and `querySelectorAll("#text-item-0")[0]` is the fallback) and waits for `ytcp-uploads-dialog`; this sequence was verified by hand in the Studio console. None of this queue/reload machinery has been run end-to-end in the browser yet.

The Studio selectors (the `*_SELECTORS` / `*_SELECTOR` / `VISIBILITY_*` constants at the top of `youtubeStudio.js` — title/description boxes, not-for-kids radio, playlist trigger/popup/done button, visibility radios and step badge) were written from memory of Studio's DOM and have not been verified against the live page — if auto-fill stops working, inspect the relevant element in the upload dialog (the banner's ✗ line says which step failed) and update those constants. The banner's "제목 복사"/"설명 복사" buttons are the manual fallback.

### 다시보기 목록의 유튜브 업로드 여부 판별 (vodList.js + youtubeVideos.js + youtubeMatch.js)

`www.sooplive.com/station/*/vod*` 목록 페이지의 "유튜브 업로드 여부 확인" 버튼이 `vodUpload:match`를 background에 보낸다. 판별 근거는 로컬 기록이 아니라 **내 채널의 실제 업로드 영상**이다: 영상 **설명의 Soop 링크(`sooplive.com/player/{titleNo}`)**로 어느 다시보기인지, **제목의 `[날짜 (n/max)]`**(파일이 하나면 `[날짜]` → 1/1)로 몇 번째 파일인지 맞춘다(`youtubeMatch.js`, 순수 함수). n은 `files` 배열 순서(1부터)이지 `file_order`가 아니다. 영상 목록은 `studio.youtube.com` 탭의 content script(`youtubeVideos.js`)가 Studio 내부 API `creator/list_creator_videos`를 SAPISIDHASH로 호출해 가져오며(열린 Studio 탭이 없으면 background가 잠깐 열었다 닫는다), 이 API의 요청/응답 형식은 기억에 의존해 쓴 것이라 **브라우저에서 검증되지 않았다** — 실패 시 에러에 응답 본문 일부가 담긴다. 결과는 콘솔과 `private-extension:vod-match` window 이벤트(`{pending, uploaded, all}`)로도 나가며, 이후 업로드 자동화가 이어받을 지점이다.

### Legacy/unused files

`src/popup.html`, `popup.js`, `styles.css`, `soopHandler.js`, `taskRunner.js`, `dummy.js` are **not referenced by `manifest.json`** — superseded by the in-page panel (`content.js`) and the options page. Don't extend them and don't assume they run; they're kept around but dead.

## Conventions

- UI copy, comments, and commit messages are in Korean; match that when editing existing files.
- Logging in the live-monitor subsystem is tagged `[LiveMonitor]` in both `background.js` and `liveMonitor.js` — keep using that tag for related additions so logs stay filterable.

# 유튜브 재생목록 영상 목록 가져오기

"재생목록 날짜순 추가"(`playlistSorter.js`) 기능이 "이 영상이 재생목록에 이미 있는지, 몇 번째에
있는지"를 판정하려면 재생목록에 실제로 들어있는 videoId 전체와 그 순서를 알아야 한다. 이 문서는
그 조회 방법을 둘러싼 긴 시행착오와 최종 결론을 정리한다. `CLAUDE.md`의 "재생목록 날짜순 추가"
절에도 요약이 있지만, 이 문서는 조회 방법 자체에 집중해 **왜 다른 방법들이 실제로 틀렸는지**를
근거와 함께 자세히 남긴다 — 나중에 "더 빠른 방법"으로 다시 바꾸고 싶어질 때, 같은 길을 다시 걷지
않기 위한 기록이다.

## 결론: Studio "동영상" 탭을 DOM으로 직접 긁는 것만 믿을 수 있다

`youtubePlaylistVideos.js`는 `studio.youtube.com/playlist/{listId}/videos` 페이지를 열어 페이지당
개수를 50으로 올리고(`ensurePageSize50`), "다음 페이지" 버튼(`ytcp-icon-button#navigate-after`)이
`aria-disabled="true"`가 될 때까지 계속 눌러가며 각 행(`ytcp-video-row`의 `a#video-title`)에서
videoId를 순서대로 모은다. **이게 완전성(차단 영상 포함)과 순서 둘 다 사람이 Studio 화면을 직접
보는 것과 동일하게 보장하는 유일한 방법이다** — 아래에 적은 두 가지 "더 빠른" 대안은 모두 실측으로
틀렸다는 게 확인됐다.

페이지 전환 대기에는 **일부러 시간 제한을 두지 않는다**(`Infinity`). 영상이 1000~2000개인
재생목록에서 이 대기가 느려지며 10초→60초로 계속 늘려도 끊기는 문제가 있었는데, 느려도 끝까지
가는 게 중간에 포기하는 것보다 낫다는 판단으로 완전히 없앴다. 셀렉터는 실제 outerHTML
(2026-10-08)을 보고 작성했다.

## 기각된 대안 1 — Studio 내부 API(`creator/list_creator_playlist_videos`) 직접 호출

DOM 스크래핑이 크고 느린 재생목록에서 타임아웃으로 끊기는 문제 때문에, Studio가 "다음 페이지"를
누를 때 내부적으로 호출하는 것과 같은 API를 직접 `fetch`로 호출하도록 바꿔봤다. 완전성(차단 영상
포함)은 보장됐지만, **이 응답의 videoId 순서가 재생목록 순서가 아니라 videoId를 알파벳(아스키)순
으로 그대로 정렬한 것이었다**는 게 실측으로 확인됐다 — 영상 1624개로 비교했더니 1593개 자리가
달랐고, 실제 배열이 `5qE85XZ1amU, 8vVe2QNsxYg, BjI7sWG6T0g, CjXe34ukzHo, ...`처럼 문자열 정렬
순서였다.

`mask`를 Studio의 실제 요청과 완전히 똑같이 맞춰도(`FULL_VIDEO_MASK`, ~60개 필드) 바뀌지 않았고,
Studio UI가 실제로 보내는 요청을 캡처해 비교해 찾아낸 `context.user.delegationContext`
(`{externalChannelId, roleType: CREATOR_CHANNEL_ROLE_TYPE_OWNER}`, "지금 로그인한 채널이 이
재생목록의 소유자로서 묻는다"는 걸 명시하는 필드)를 추가해봐도 **바뀌지 않았다**. 이 필드가
빠져서 알파벳순 기본값으로 응답했다는 가설이었는데, 추가한 뒤에도 알파벳순 그대로였다 — 즉
이 API로는 재생목록의 실제 추가 순서를 가져올 방법을 끝내 못 찾았다. (channelId를 페이지의
`ytcfg` `CHANNEL_ID` 키에서 읽는 것부터가 애초에 그 키가 실제로 있는지 불확실한 추측이었다는
점도 있다 — 이 프로젝트의 다른 코드(`studioChannelId:get`)는 channelId를 URL 경로에서 읽지,
Studio ytcfg를 스크래핑하지 않는다.)

## 기각된 대안 2 — 공개 재생목록 페이지 순서 + watch 패널로 차단 영상 위치 복원

대안 1이 완전성은 되는데 순서가 안 되니, 반대로 **공개 재생목록 페이지**
(`www.youtube.com/playlist?list=...`)의 순서(각 영상이 명시적인 `index` 필드를 들고 있어 정확함)
를 쓰고, 그 페이지에 아예 안 보이는 차단 영상만 따로 위치를 알아내 끼워 넣는 하이브리드를
시도했다.

- 공개 페이지 1페이지는 background의 순수 `fetch()`로 받아야 순서가 정확했다 — 실제 탭을 열어
  하이드레이션된 뒤의 `window.ytInitialData`를 읽으면 1페이지부터 순서가 어긋났다(로그인한 소유자
  보기에서 클라이언트가 다시 정렬하는 것으로 추정, 미확인).
- 다음 페이지(continuation, `/youtubei/v1/browse`)는 background에서 직접 POST하면 `Origin` 헤더가
  `chrome-extension://...`로 나가(fetch로 조작 불가) 403으로 막혔다 — 그래서 그 한 건만 실제
  `www.youtube.com` 탭의 content script에 중계시켰다(`youtubePlaylistOrder.js`, 지금은 삭제됨).
- 1페이지와 continuation 페이지는 스키마가 달랐다(`playlistVideoRenderer` vs 신형
  `lockupViewModel`, `continuationItemRenderer` vs `continuationItemViewModel` — 토큰 경로 자체가
  다름). 두 스키마를 각각 처리하도록 짜서 겨우 전체를 받아낼 수 있었다.
- **차단된 영상의 실제 위치는 그 videoId의 watch+list 페이지(`watch?v=<id>&list=<playlistId>`)가
  내려주는 "다음 영상" 패널의 `twoColumnWatchNextResults.playlist.playlist.currentIndex`(0부터)로
  알아내려 했다.** 처음 테스트(차단 영상 1개)에서는 값이 정확해 보였고(16, 주변 패널 항목들의
  순서도 공백 없이 이어짐), 16개 차단 영상에 대해 순차 조회(동시 요청은 서로 값이 섞이는 문제가
  있어서 순차로 바꿈)로 확장해도 그럴듯한 값들이 나왔다.
- **그런데 이 `currentIndex`가 실제로는 버그가 있다는 게 결정적으로 확인됐다.** 사용자가 새
  재생목록을 만들어 일반 영상들을 순서대로 추가하다가, 중간 어딘가에 차단된 영상 하나를
  추가하고 그 영상의 watch+list 페이지를 열어봤더니 **"1/28"(28개 중 첫 번째)로 나왔다** — 실제로는
  중간에 넣은 영상인데 첫 번째라고 알려준 것이다. 이전의 "그럴듯해 보인 값들"은 우연이었을
  가능성이 크고, 이 필드는 차단된 영상에 대해서는 전반적으로 믿을 수 없다.

이 가설이 깨지기 전까지 "서로 이웃한 차단 영상 여러 개가 같은 `currentIndex`를 보고하는 경우"(둘
이상의 차단 영상이 정확히 같은 값을 주는 현상)까지 발견해 묶어서 처리하는 로직까지 만들었었는데,
돌이켜보면 그 현상 자체가 이미 "이 필드가 차단 영상에 대해서는 신뢰할 수 없다"는 신호였다.

## 요약: 두 "지름길" 모두 처음부터 불가능했다

- Studio API 응답 순서 → **처음부터 재생목록 순서가 아니었다**(알파벳순). mask/권한 필드를 아무리
  맞춰도 고쳐지지 않았다.
- watch 패널의 `currentIndex` → **차단된 영상에 대해 버그가 있어 믿을 수 없다**(실측: "1/28"
  오보).

두 소스 모두 간접적으로 서버 내부 상태에 의존하는 "편리해 보이는" 데이터였고, 사람이 Studio
화면에서 직접 페이지를 넘기며 보는 것(DOM 스크래핑)만이 실제로 검증된 유일한 방법이다. 느리다는
단점은 "다음 페이지 대기에 시간 제한을 두지 않는다"로 감당하기로 했다 — 틀린 데이터보다 느린
정확한 데이터가 낫다.
